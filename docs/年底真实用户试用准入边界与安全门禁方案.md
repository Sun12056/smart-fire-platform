## 1. 目标、范围与非目标

### 1.1 目标

在不产生真实消防处置后果的前提下，让 ≤20 名真实用户在受控域名上完整体验"监测 → 报警 → 疏散决策 → 方向下发"主链路，并保证：

1. 只有被授权的人能进入；
2. 演示永远不被误读为真实处置；
3. 试用环境与任何生产资源物理隔离；
4. 每一次放量都能追溯到具体代码与部署版本；
5. 出问题时数据可恢复、代码可回滚。

**语义前提（v1.2 统一口径，§3 / §4 一致遵守）**：

- 试用期内"疏散执行""路线确认""方向下发"一律指**模拟语义** —— 只改变模拟状态与界面展示；
- 系统**不存在**向真实消防设备下发指令的通道，且本轮**不新增**该通道；
- "真实执行"是一个**尚未实现的 Stage 3 概念**，不是试用阶段的验收对象（详见 §4.5 三段式边界）。

### 1.2 范围

- 单建筑（`Building` 单实例）；
- 人员、设备、出口运行态均为**脱敏或模拟**数据；
- 试用期：2 周（D8 待确认）；
- 试用域名独立（如 `trial.<domain>`）。

> **v1.3.3 注**：以上"单建筑 / 脱敏 / 2 周 / ≤20 人"分别是 **D2、D8 的默认建议**在当前方案中的**假设性表述**，不是已批准的范围。D2/D8 未确认前，本节的任何表述都不得被引用为"试用范围已定"。若 D2/D8 改为其它取值，本节与 §5.2、§12.1 需联动复核。

### 1.3 非目标（本轮明确不做）

- 不接入真实消防主机 / 真实出口状态上报（Stage 3 之后）；
- **不新建真实执行接口**：不得为通过 G-07 验收而提前制造 `POST .../execute`、`dispatch` 之类端点（v1.2 §4.5）；

## 2. 准入边界模型

### 2.1 三层边界

| 层 | 边界内容 | 失效后果 |
|---|---|---|
| L1 身份边界 | 谁能进、以什么角色进 | 未授权者读写人员位置、篡改方案 |
| L2 语义边界 | 系统说的"疏散完成"指的是什么 | 把模拟结果当成真实撤离结论 |
| L3 执行边界 | 什么条件下才允许"真实执行" | 对真实场景下发了未经确认的指令 |

**三者缺一不可**：L1 通过但 L2 缺失，等于给陌生人一把看起来像真钥匙的假钥匙；L2 通过但 L1 缺失，等于把演示台交给公网。

### 2.2 五条红线（任何一条不满足，禁止放量）

1. **匿名可读人员位置** → 禁止放量。
2. **任何"仅凭请求头存在"判定身份** → 禁止放量。
3. **真实出口状态缺失却允许真实疏散执行** → 禁止放量（Stage 3 语义）；试用期的**等价要求**是"真实执行入口不存在"（§4.5 段 A），二者不可互相替代。
4. **试用环境与生产共用 D1 / Worker / Secrets** → 禁止放量。
5. **发布产物无法追溯到 Git Commit SHA** → 禁止放量。

## 3. 身份认证与授权（修正 1｜SEC-001～SEC-004）

### 3.1 现状事实（核验）

| 事实 | 证据 |
|---|---|
| 全 Worker 仅注册一个中间件 `cors`，无鉴权中间件 | `worker/src/index.ts:26` |
| 唯一"凭证"判定是对 `X-Seed-Token` 的等值比较，只保护 `/api/v1/admin/seed` | `worker/src/routes/admin.ts:14` |
| 全部业务 REST（建筑/设备/遥测/告警/巡检/人员/日志/预案/演示）无鉴权 | `worker/src/index.ts:36-49` |
| WebSocket 升级只校验 `Upgrade: websocket`，无身份、无 Origin 校验，连接即下发全量快照 | `worker/src/durable/DemoRoom.ts:140-150` |
| WS 入口 `GET /api/v1/demo/ws` 直接把原始请求转给 DO，`sessionId` 取自 URL query，默认 `default` | `worker/src/routes/demo.ts:43-46` |
| 仓库自述："业务 REST 接口当前未实现鉴权（已知遗留项）" | `README.md:758` |
| 代码中不含 `Authorization` / `Bearer` / `JWT` / `CF-Access` 相关实现 | 全 `worker/src` 检索 0 命中 |

### 3.2 目标方案（D1 建议：B 方案）

**Cloudflare Access 承担"人"的认证，Worker 承担"授权"的最终判定。**

1. **边缘层**：Cloudflare Access 保护 `trial.<domain>` 与 `api-trial.<domain>`，仅允许邮箱白名单（≤20 人）通过 IdP 登录。
2. **应用层（Worker 必须独立验签）**：Worker 不信任"请求到达就代表已认证"，对每个受保护请求自行验证 Access JWT：
   - 取票位置：`Cf-Access-Jwt-Assertion` 请求头，或 `CF_Authorization` Cookie；
   - 公钥：`https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`，按 `kid` 缓存（建议 1h，未命中回源，回源失败即拒绝）；
   - **算法白名单固定为 `RS256`**，显式拒绝 `none`、`HS*`、算法混淆；
   - 必须校验且全部失败即拒：`iss` 精确等于 `https://<team>.cloudflareaccess.com`；`aud` 等于为本应用签发的 AUD tag；`exp` / `nbf`（允许 ≤60s 时钟偏移）；`iat` 不晚于当前时间；
   - 用 WebCrypto（`crypto.subtle.importKey` + `verify`）验签，不使用第三方库以免引入算法歧义；
   - 校验失败一律返回 401，且**不区分**"无票 / 票伪造 / 票过期"的具体原因（避免探测），细节只进服务端审计。
3. **角色映射必须在 Worker 内完成**：
   - 映射键：JWT 的 `email`（或 `sub`），**不得**使用任何请求头里的 role/group 字段；
   - 映射表：D1 表 `trial_users(email, role, building_id, enabled, created_at)`，或 `[env.trial.vars]` 只读 JSON（二选一，D1 便于审计，推荐 D1）；
   - 角色（能力边界见 §3.5）：`viewer`（只读展示）、`operator`（**仅可**执行模拟路线确认与模拟方向展示，**不得向真实设备下发任何指令**）、`demo_operator`（可推进演示六阶段）、`admin`（配置与导出，同样不得下发真实指令）；
   - 未命中映射 / `enabled = 0` → 403，**不做默认放行**。
4. **默认拒绝**：每条路由显式声明所需 role；未声明的路由视为 `admin`，未声明且未认证即 401。禁止"忘记加声明就等于公开"。
5. **禁止的伪鉴权（明确写死为反模式）**：
   - ❌ 只检查 `Cf-Access-Jwt-Assertion` 头是否存在；
   - ❌ 只检查 `CF-Access-Authenticated-User-Email` 头（该头可被边缘注入，但应用层无法自证其未被绕过）；
   - ❌ 信任客户端自带的 `X-User` / `X-Role` / `X-Building-Id`；
   - ❌ 用共享静态 Token 代替用户身份（`X-Seed-Token` 仅限 seed，且生产禁用）。

### 3.2.1 JWT 验证契约（v1.3 补充，逐项可判定）

| ID | 契约项 | 要求（必须） | 不满足时 |
|---|---|---|---|
| J-01 | `aud` **类型与匹配**（v1.3.1 定框架，v1.3.2 明确"三选一由样本决定"） | **已由官方文档确认**：每个 Access 应用有唯一 AUD tag，`aud` 声明表示 token 对哪个应用有效，AUD 不变（除非删除/重建应用）。**官方文档未明确 `aud` 的 JSON 类型**，示例均以单个字符串传入。<br>**格式结论须由实际签发样本确定**，候选只有三种：仅 `string` / 仅 `string[]` / 两者皆可；**在取得样本前，按最严格口径只接受 `string`**。<br>① `string`：必须与配置的 AUD tag **全等**（区分大小写、除 trim 外不做改写）；<br>② `string[]`：**仅在样本确认后启用**；启用时要求数组长度恰为 1 且唯一元素与本应用 AUD 全等（多元素视为跨应用令牌，拒绝）；<br>③ 未取得样本前，数组形式一律拒绝并记录待核验，不得"为兼容先放过" | 401（不记录具体原因） |

| J-03 | `iss` | 精确字符串相等（含协议与端口）；末尾多/少一个 `/` 视为不匹配 | 401 |
| J-04 | 时间类声明 | `exp` / `nbf` / `iat` 必须为数值（秒）；允许 **≤60s 时钟偏差**，仅用于放宽 `exp` 与 `nbf`；`iat` 晚于 `now + 60s` 视为非法 | 401 |
| J-05 | `kid` 未命中（含**回源并发控制**，v1.3.1 补充） | 禁止用其它 key "试签"；允许**回源 JWKS 一次**，且必须满足：<br>① **single-flight**：同一 `kid` 同时最多 1 个回源请求，其余请求等待该结果或直接拒绝（不得各自发起）；<br>② **冷却**：同一 `kid` 回源冷却 ≥60s；<br>③ **全局限速**：JWKS 回源总速率 ≤1 次/秒（防止未知 `kid` 洪水导致对 IdP 的请求放大）；<br>④ **未知 kid 计数与熔断**：单位时间未知 `kid` 超阈值（建议 100 次/分钟）时暂停回源、直接拒绝并告警；<br>⑤ 回源后仍无该 `kid` → 401 并记录（含 kid 前 8 字符）；<br>⑥ **禁止**降级为"不验签放行"或"跳过 kid 用第一个 key" | 401 / 429 + 审计 |
| J-06 | JWKS 轮换（依据官方文档修正） | 官方文档：Access **默认每 6 周轮换签名密钥**，旧密钥在轮换后**继续有效 7 天**；`/cdn-cgi/access/certs` 同时返回**当前密钥与上一把已轮换密钥**（`keys` / `public_certs` 含两把），并要求**按 JWT 的 `kid` 匹配 `public_certs`**、不要取 `public_cert` 当前值（可能读到过期缓存）。据此：<br>① 缓存 TTL ≤1h，缓存内**必须支持 ≥2 个 kid 并存**；<br>② 必须按 `kid` 选择密钥，禁止按数组顺序取第一把；<br>③ 尊重响应 `Cache-Control`；<br>④ 回源失败时过期缓存最多再用 1 个 TTL，之后必须拒绝（fail-closed）；<br>⑤ 禁止硬编码公钥（官方明确建议走端点校验） | 401 |
| J-07 | **身份映射优先级** | 映射主键优先 `sub`（不可变），`email` 仅作展示与人工核对；**若 `sub` 存在则角色绑定只认 `sub`**；`email` 变更不得导致角色漂移；`sub` 缺失时才回退用 `email`（并记录降级） | 401 / 403 |
| J-08 | 大小写与规范化 | `sub` 区分大小写、禁止 `trim` 后比较以外的改写；`email` 比较不区分大小写并按 IDNA 规范化域名；映射表中同一 `sub` 不得存在多条启用记录 | 403 + 审计 |
| J-09 | **签名算法固定**（v1.3.1 新增） | 只接受 `alg = RS256`（官方文档：JWKS 中 JWK 为 `kty=RSA`、`alg=RS256`、`use=sig`；手动校验步骤要求"Select the RS256 algorithm"；Python 示例 `algorithms=['RS256']`）。<br>① **不得**根据 JWT 头里的 `alg` 动态决定允许的算法（即"跟着 token 走"），`alg` 只用于**校验是否等于唯一允许值**；<br>② 密钥选择必须同时符合**预期算法与用途**：JWK 必须 `kty=RSA` 且 `use=sig`；`use` 缺失时按 `alg=RS256` 白名单兜底但须记录；<br>③ 拒绝 `none` / `HS*` / `RS384` / `PS*` 等一切非 RS256，以及 `kty` 非 RSA 或 `use` 非 sig 的密钥 | 401 + 审计（记录不匹配原因） |
| J-10 | **密钥来源固定**（v1.3.1 新增） | 只允许从本团队域的 `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs` 取 JWKS；禁止硬编码公钥、禁止从可配置 URL 取（防 SSRF/降级）；端点返回的 `keys` 与 `public_certs` 视为同一密钥集的两种表示，任一缺失不影响按 `kid` 匹配 `keys` | 401 |

**依据说明（J-01/J-02/J-05/J-06/J-09/J-10）**：

- 上述算法（RS256、`kty=RSA`、`use=sig`）、JWKS 端点、`kid` 匹配方式、轮换周期（6 周 / 旧密钥 7 天）、`iss` 格式、AUD 语义，均取自 Cloudflare 官方文档 **《Validate JWTs》**（`developers.cloudflare.com/cloudflare-one/identity/authorization-cookie/validating-json/`，页面标注最后更新 2026-11-02）；
- **`aud` 的 JSON 类型官方文档未明确**：示例均为单字符串，故"数组形式"标注**待核验**（须用真实 token 解码确认后才可启用），本文件不对此作已确认断言；
- 官方推荐的头部为 `Cf-Access-Jwt-Assertion`（cookie 不保证传递），与 §3.2 第 2 条一致；
- 本轮未获取任何真实 token、未访问 Cloudflare 账号，上述"待核验"项在核实前不得视为已满足。

**补充约束**：

- J-05 / J-06 的错误必须区分"网络失败"与"key 不存在"：前者可重试一次，后者不得重试；
- 验签实现只允许使用平台 WebCrypto（`crypto.subtle`），**不得**引入可配置 `alg` 的第三方解码库；
- 所有拒绝路径统一返回 401/403，响应体不含 `kid`、`iss`、`aud` 等诊断信息（诊断只进服务端审计）。

### 3.3 WebSocket 票据（修正 1 后半）

WS 无法携带自定义头，**但仍不得把长期 Token 放入 URL**。方案：

1. `POST /api/v1/auth/ws-ticket`（需已认证 JWT）→ 返回 `{ ticket, expiresIn: 60, sessionId }`；
2. ticket = 32 字节随机值（base64url），服务端只存 **SHA-256 哈希**，落 D1 `ws_tickets(ticket_hash, sub, session_id, expires_at, used_at)`；
3. WS 升级：`GET /api/v1/demo/ws?ticket=...`，服务端执行**原子一次性消费**（`UPDATE ws_tickets SET used_at=? WHERE ticket_hash=? AND used_at IS NULL AND expires_at > ?`），影响行数 ≠ 1 即拒绝升级；
4. 票据绑定 `sub` + `sessionId`，不可跨会话复用；TTL 60s，过期即作废；
5. 升级时同时校验 `Origin` 属于允许列表（与 CORS 白名单同源，`worker/src/index.ts:25-32` 已有 `PROD_ORIGIN` / `ALLOWED_ORIGINS` 基础）；
6. ticket 出现在 URL query 会进入边缘访问日志 —— 缓解措施：一次性 + 60s + 无权限提升 + 日志保留期限 ≤7 天，并**在风险登记中保留该残余风险**（§12）。

## 4. Demo 与真实疏散隔离（修正 2｜BIZ-001）

### 4.1 语义定义（本文的强制口径）

> **Demo 六阶段只改变模拟状态，不代表真实消防处置，也不代表人员撤离完成。**

### 4.2 现状事实（核验）——两处与审查意见冲突，必须修

| 问题 | 事实 | 证据 |
|---|---|---|
| 出口运行态从未真实上报 | 世界初始化即 `defaultExitStates()`（全 OPEN），快照把它当作"已上报" | `worker/src/demo/engine.ts:79-81`；`shared/evacuation/exitRuntime.js:23-25`；`worker/src/durable/DemoRoom.ts:604` |

- 前端只有 `POST /api/v1/demo/command` 与 `demo/reset`（`src/services/demoService.js:38-45`），执行是本地模拟 `startEvacuationRun()`（`src/stores/fireStore.js:2018`）；
- 因此本阶段的门禁内容是"**入口不存在**"（负向断言 E-5），**不是**"拒绝请求"；
- **严禁**为凑齐"拒绝逻辑"而先造一个真实执行端点 —— 那会把"不存在"变成"存在但可能绕过"，净安全收益为负。

**R2.2-B Stage 3（未来）：服务端出口状态门禁（预置契约，本轮不验收）**
若将来引入真实执行接口，则必须以服务端为准，且不得复用当前 Demo 语义：

- 若执行所需任一出口的 `source !== real` 或状态无效 → **拒绝**（HTTP 409/412），返回原因码（如 `EXIT_STATE_NOT_REAL`）；
- 拒绝发生在服务端，**前端置灰仅为 UX，不构成安全边界**；
- 拒绝事件写入审计日志；
- 引入真实通道时所有出口必为 `unknown`，规则生效后"真实执行"将被**恒定拒绝** —— 这是正确行为，不是缺陷；
- 该段落的验收用例为 B-1 / B-2，**仅在真实接口实现后启用**，不属本轮门禁。

### 6.2 强制要求（v1.2 修正：以"归档构建"替代"工作区干净"）

1. **构建源 = 指定 Git Commit 的归档**：在独立目录执行 `git archive <SHA> | tar -x -C <build_dir>`（或 `git worktree add --detach <build_dir> <SHA>`），构建只在该目录内进行。
2. **不要求开发工作区无未跟踪文件**：v1.1 曾要求"构建前 `git status --porcelain` 必须为空"，与必须保留 19 项未跟踪文件相矛盾，v1.2 取消该要求。判定依据从"工作区是否干净"改为"**构建输入是否只来自归档**"。
3. **产物纯净性验证**（三条同时满足才算 PASS）：
   - **输入集合比对**：归档解包目录内的全部文件 ⊆ `git ls-tree -r --name-only <SHA>` 的受跟踪集合；

4. 产物清单需可复核：文件数、总字节、每个文件 SHA256，存档到 `docs/release/`（后续实施项）。
5. **不得**为通过门禁而删除或 `git add` 未跟踪文件（明确禁止，见 §11）。

> 与 §11 的一致性：本门禁与"保留未跟踪文件"**不冲突** —— 未跟踪文件只要不进入归档目录，就不会进入产物；反之，即使工作区干净，若构建读取了工作区而非归档，仍判不合格。

#### 6.3.1 自动部署（Pages Git 集成）的追溯取证（v1.3.1 新增）

当 Pages 由 Git 集成自动构建发布时，**发布行为发生在平台侧**，仓库内没有任何记录可证。取证步骤必须按序执行，任一环缺证即按表后规则判定：

| 步骤 | 取证动作 | 期望结果 | 缺证时判定 |
|---|---|---|---|
| P-1 | 打开该次 Pages deployment 详情（或调 API），读取 `deployment_id`、`environment`（preview/production）、`url` | 三者齐全且 URL 可访问 | **待核验**（不得判 FAIL 也不得判 PASS，先补齐） |
| P-2 | 在同一详情中读取该次部署对应的 **commit SHA**（或从构建日志的环境变量 `CF_PAGES_COMMIT_SHA` 读取） | 40 位 SHA，且 `git cat-file -e` 在仓库存在 | **FAIL**（"部署产物无对应 commit"即不可追溯） |
| P-3 | 记录触发方式（Git 集成 / 手动 / API），并记录触发来源（分支名、提交标题） | 与 `deploy_trigger` 一致 | 写 `unknown` + **待核验** |
| P-4 | 将 P-1～P-3 的截图/API 响应存入发布记录（`evidence`） | 三项信息同一屏可对照 | **待核验** |
| P-5 | 用 P-2 的 SHA 重新归档构建（§6.2），比对 `artifact_digest` 与线上产物 | 一致 | **FAIL**（产物与来源不符） |

**判定规则**：

1. **不得**用本地 `git rev-parse HEAD` 填充 `commit_sha` —— 本地 HEAD 与平台实际部署无因果关系；
2. **不得**仅凭 `README.md:711,715` 的"推送 main 后 Pages 自动构建发布"认定"平台已启用自动部署"—— README 是文档声明，不是平台配置证据；
3. 平台侧无法提供 commit SHA 时，G-12 判 **FAIL**（而非"待核验"）；只能提供 deployment id 但无 commit 的，同样判 FAIL；
4. 自动部署发生在受控分支之外（如任意分支可发布生产）时，判 **FAIL** 并记入 D4 待处理项；
5. `待核验` 只能用于"证据尚在收集中且未用于放量决策"，**不得**在放量评审时仍为待核验。

#### 6.3.2 证据层级：配置声明 / 构建记录 / 平台实际部署记录（v1.3.2 新增）

| 层级 | 定义 | 典型例子 | 能否作为"部署已完成且可追溯"的证据 |
|---|---|---|---|
| **L1 配置声明** | 仓库内的配置与文档表述 | `README.md:711,715` 称"通过 GitHub 仓库集成部署 / 推送 main 自动发布"；`.github/workflows/ci.yml` 无 deploy 动作 | **不能**（声明 ≠ 事实；CI 无 deploy ≠ 平台不部署） |
| **L2 构建记录** | 本地或 CI 的构建输出 | `npm run build` 日志、`dist/` 文件与哈希、GitHub Actions 日志 | **不能**（只证明"构建过"，不证明"平台部署的是它"） |
| **L3 平台实际部署记录** | Cloudflare 侧的部署实体 | Pages Deployments 列表/API（deployment id、环境、URL、commit、触发方式）；Worker 部署回读（deployment id、version id、生效 bindings） | **唯一**可作为 PASS 依据 |

**判定规则**：

1. `pages_deployment_id` / `commit_sha` / `deploy_trigger` **只能**由 L3 填充；L1/L2 只能作为辅助说明，须显式标注层级（如"L2 构建日志"）；
2. **不得**由 L1 推断"平台已启用自动部署"；**不得**由 L2（含 GitHub Actions 日志）推断"Cloudflare 实际部署的是该构建"；
3. L3 未取得时：相应字段写 **`待核验`**，G-12 不得判 PASS；若放量评审时仍缺 L3，直接判 **FAIL**；
4. L3 与 L2 冲突（平台记录的 commit ≠ 记录的构建 commit）→ 以 L3 为准，并判 **FAIL**（产物来源不符）；
5. 平台未提供 commit 关联时：**不得**用"同一时间段唯一一次提交"之类推测填充，只能标 `待核验`。

### 6.4 Worker 后端部署产物记录（v1.3 新增，独立台账）

| 字段 | 要求 | 采集方式 |
|---|---|---|
| `commit_sha` | 完整 40 位，与 Pages 记录一致；**必须是实际部署对应的 SHA** | 取自部署记录：`wrangler deployments list --env trial` 的版本信息，或部署时注入的构建标注（如 `--var BUILD_SHA:<sha>`，落地属后续编码项）。**禁止用本地 `git rev-parse HEAD` 代替** |
| `build_env` | Node 版本、wrangler 版本、目标环境 `--env trial`、OS | 部署日志 |
| `dry_run_digest` | `wrangler deploy --env trial --dry-run` 输出摘要：`name` / `main` / D1 `database_name` + `database_id` / bindings 列表 | dry-run 输出（脱敏后存档） |
| `bundle_manifest` | 打包产物（`--outdir` 或 dry-run 产物）每文件 SHA256 + 汇总 | 部署后统计 |
| `lockfile_sha256` | `package-lock.json`、`worker/package-lock.json`（若存在）各自 SHA256 | `Get-FileHash` |
| `config_sha256` | `worker/wrangler.toml` 的 SHA256（记录"部署的是哪份配置"） | 同上 |
| `worker_name` / `worker_version_id` | trial Worker 名与版本 id | `wrangler deployments list --env trial` |
| `worker_deployment_id` | 部署记录 id（**部署后回读确认**，非部署前预估） | `wrangler deployments list --env trial` 或平台侧部署记录；须与 `worker_version_id` 对应 |
| `evidence` | 部署输出 + 回读结果原文（含 deployment id、版本 id、commit 标注） | 存档到发布记录目录 |
| `bindings_effective` | 实际生效的 D1 / DO / vars 名称（值脱敏） | 平台侧 |
| `secrets_names` | 配置的 secret **名称清单**（严禁记录值） | 平台侧 |
| `deployed_at_utc` / `operator` / `approver` | 同上，且审批人 ≠ 执行人 | 发布单 |

#### 6.4.1 Worker 实际部署 SHA 的取证要求（v1.3.1 新增）

| 项 | 要求 |
|---|---|
| 取得方式 | 部署后立即 `wrangler deployments list --env trial`（或平台侧部署详情）读取**该次部署**关联的版本信息；若平台不直接暴露 commit，则要求部署命令携带构建标注并随部署记录留存 |
| 禁止做法 | ①用本地 `git rev-parse HEAD` 填 `commit_sha`；②用 `package.json` 版本号代替 commit；③用"最近一次 CI 通过的分支"推断 |
| 可接受的最低证据 | deployment id + 版本 id + 部署时间 + 与该时间对应的构建标注（或构建日志中记录的 SHA）四者能互相印证 |
| 缺证判定 | 无 commit 关联 → G-12 **FAIL**；仅有 deployment id 但无版本/构建标注 → **FAIL**；`--dry-run` 输出不能代替实际部署记录 |

#### 6.4.2 Worker 侧证据层级与字段来源（v1.3.2 新增）

| 字段 | 取得方式 | 证据层级 | 禁止做法 |
|---|---|---|---|
| `commit_sha` | 部署时注入的构建标注回读，或平台部署详情中的提交关联 | **L3** | 用本地 `git rev-parse HEAD`、用 `package.json` 版本号、用"最近一次 CI 通过的分支"推断 |
| `worker_version_id` | `wrangler deployments list --env trial` / 平台部署详情 | **L3** | 部署前预估 |
| `worker_deployment_id` | 同上，**部署后回读** | **L3** | 用 `--dry-run` 输出代替 |
| `bindings_effective` / `secrets_names` | 平台侧生效配置（控制台或 `wrangler deployments view`） | **L3** | 用 `worker/wrangler.toml` 文件内容代替"实际生效配置"（文件属 L1，可能与线上漂移） |
| `dry_run_digest` | `wrangler deploy --dry-run` 输出 | **L2** | 不得据此声称"已部署" |
| `config_sha256` | `wrangler.toml` 文件哈希 | **L2** | 同 L2 限制 |

**判定**：Worker 台账中除 `dry_run_digest` / `config_sha256` 外，**均须为 L3**；任一为 L1/L2 顶替，G-12 判 `待核验`；若以 L1/L2 冒充 L3，判 **FAIL**（记录造假）。

### 6.5 两份产物的一致性约束

1. **同一次发布 = 同一个 `commit_sha`**：Pages 与 Worker 记录中的 SHA 必须相同；不同 SHA 视为"混版发布"，G-12 直接 FAIL；
2. **两份产物指纹不可互相替代**：Pages 的 `artifact_digest` 与 Worker 的 `bundle_manifest` 分别记录，缺一即 FAIL；
3. **自动发布也必须留痕**：若 Pages 由 Git 集成自动构建，`pages_deployment_id` 与 `deploy_trigger=pages-git-integration` 必须在发布后**回填**；未回填视为"不可追溯"；
4. **配置变更单独记录**：`wrangler.toml` / Pages 构建设置的任何改动，都要在发布单中列出 diff 摘要（配置漂移是最常见的"产物对了、行为错了"来源）；
5. **撤销/回滚记录**：回滚到旧产物时，记录"回滚目标 deployment id + 原因 + 执行人"，并注明数据库是否同步回滚（§8.3：代码回滚 ≠ 数据库回滚）；
6. **SHA 来源必须为平台侧**（v1.3.1）：两份台账的 `commit_sha` 都不得取自本地 HEAD；若平台未能提供 commit，视为"来源不可追溯"，G-12 FAIL；
7. **自动发布不得"事后补记"为人工发布**：`deploy_trigger` 必须如实记录；把 `pages-git-integration` 记成 `manual` 属记录造假，一经发现按 G-12 FAIL 处理并复核历史发布；
8. **证据留存与记录同等重要**：`evidence` 缺失时，即使字段填齐也判 `待核验`，不得据此放量；
9. **三层证据不得混用**（v1.3.2）：配置声明（L1）、构建记录（L2）、平台实际部署记录（L3）必须在发布记录中**分别标注层级**；只有 L3 可作为 PASS 依据。用 L1 推断"平台已自动部署"、用 L2（含 Actions 日志）推断"平台部署的就是该构建"，均判为**证据不足**（待核验），不得写成"已验证"。

**硬规则（v1.3.1 强化）**：

1. **标记不是隔离**：命名/前缀只能事后区分，不能阻止写入；物理隔离仍由 D3（trial 独立 D1）承担；
2. **标记必须由服务端生成并校验**：客户端不得指定 `module` / `type` / `id` 及其前缀；服务端生成后须在写入前校验一次（防内部代码绕过）；
3. **命名约束的覆盖面必须逐入口登记**（本节即登记表），新增写入入口未登记即视为门禁失效；
4. **凡无 `origin` 列的表，标记字段即事实来源**：判读规则写进 `API_CONTRACT.md`，避免各端各自解释；
5. **未覆盖项不因"设计已写"而视为已解决**：上表所有"未覆盖"都是后续编码项，未实现前 G-04/G-08 不能判 PASS。

##### 7.5.3.6 统一原则与"前缀/过滤 ≠ 隔离"（v1.3.2 新增）

**统一原则（三张表一律适用，不因表而异）**：

| # | 原则 | 具体要求 | 责任方 |
|---|---|---|---|
| U-1 | **来源判定由服务端负责** | 由"调用路径 + 命令类型 + 目标行"判定，不由请求参数声明；同一命令在不同路径下可判定为不同来源 | 服务端 |
| U-2 | **标记生成由服务端负责** | `module` / `type` / id 前缀 / `origin` / `session_id` / `actor_sub` 全部由服务端生成；客户端提交这些字段**一律 400 并记审计**（v1.3.4 统一口径，删除"忽略"降级写法） | 服务端 |
| U-3 | **权限检查由服务端负责** | 按 §3.5 角色矩阵 + 目标行来源双重校验；前端置灰不构成权限 | 服务端 |
| U-4 | **客户端提交的标记不可信** | 任何"客户端告诉我这是模拟数据"的说法不采纳；收到即拒绝（400）并审计 | 服务端 |
| U-5 | **关闭而非绕过历史入口** | `operation_logs` 的匿名 POST 必须**移除/禁用**（而非"加了服务端写入就算修好"）；`alarms`/`evacuation_plans` 的客户端 `id` 输入必须改为服务端生成 | 服务端 |

**"前缀 + 过滤"不是数据隔离（必须显式承认的局限）**：

| 做法 | 能解决 | **不能**解决 |
|---|---|---|
| `-DEMO` / `DEMO-` 命名前缀 | 事后区分、减少误读 | 阻止写入；防伪造（客户端可造同名）；跨表一致性；误删误改 |
| 查询/统计/导出过滤 | 展示层不混淆 | 数据本身仍混在同一库同一表；绕过 API 直连数据库仍可见；过滤条件写错就全盘失效 |
| 增加 id 命名空间 | 降低 `INSERT OR REPLACE` 撞行概率 | 不是约束（DB 无强制）；不是权限（谁都能用该前缀写） |

因此：

1. **数据隔离的唯一可靠手段是库级/表级物理分离**（trial 独立 D1 已由 D3 覆盖）；
2. 前缀与过滤是**必要但不充分**的辅助手段，须与 §7.5.7 的 `origin` 字段 + 服务端写入逻辑 + DB 约束共同使用；
3. **不得**在任何汇报中把"已加前缀 / 已加过滤"表述为"已完成数据隔离"（对应 RSK-11 仍未解决）；
4. **KPI 口径单独要求（v1.3.5，P2-5）**：告警处置闭环率、平均处置时长、方案采纳率等 KPI **必须**采用 **`origin='real'` 白名单**（仅 `real` 计入；`unknown` 单列且不计达成率；`simulated`/`test` 排除）；**仅以"排除 `simulated`/`test`"实现不构成 PASS**（黑名单会漏掉未登记来源）；未实现白名单的 KPI 不得对外展示，也不得作为试用结论依据。逐域指标定义见 **§3.4.1-A**；读取口径见 §7.5.3.7。

#### 7.5.4 trial 库的数据来源分层与保护（v1.3.1 重写：取消"全模拟库"前提）

**先更正 v1.3 的错误推导**：

> v1.3 写："trial 库按 BIZ-001 现状不含任何真实处置数据（出口状态从未真实上报），因此 'trial 库 = 全模拟库' 是逻辑闭环。"

该推导**不成立**，三点理由：

1. **出口状态只是一类数据**，不能代表整库：即使出口从未真实上报，`buildings` / `devices` / `person_presence` / `telemetry` / `alarms` / `operation_logs` 仍可能承载真实基础资料、真实人员位置、真实身份与真实操作记录；
2. **"某类数据尚未接入"不等于"该类数据不存在"**：接口存在即可能被写入（`telemetry.ts:24,36`、`personPresence.ts:74`、`alarms.ts:35` 都是开放写入通道）；
3. **"全模拟库"一旦成为结论，就会成为降低保护等级的理由** —— 这正是本轮要消除的风险。

**"出口状态未接入" ≠ "以下数据是模拟数据"（v1.3.2 显式列举）**：

| # | 不能因此认定为模拟的数据 | 现状依据 |
|---|---|---|
| 1 | **建筑基础资料**（`buildings`：名称、层数、类型、巡检率） | `buildings` 表为静态台账，`seed.ts:29` 仅写入 mock；真实建筑资料导入路径**待核验** |
| 2 | **楼层 / 房间 / 区域（zone）划分** | 存于 `devices.zone` / `person_presence.zone` / `evacuation_plans.start_area`；来源**待核验** |
| 3 | **设备基础资料**（`devices`：类型、安装位置、可控性、额定参数） | `devices.ts:29` 允许 PATCH 修改，属可写台账 |
| 4 | **真实设备在线 / 故障状态** | `devices.status`（normal/warning/fault/emergency）、`devices.communication`（online/offline）、`battery`/`signal`/`temperature` 等字段可由遥测更新（`telemetry.ts`） |
| 5 | **真实告警** | `alarms.ts:35`（POST）/`:76`（PATCH）为开放写入通道，可产生非 `-DEMO` 告警 |
| 6 | **真实人员位置** | `personPresence.ts:74`（batch 上报） |

**结论**：出口运行态只是**一类**观测数据，其缺失不能推导整库性质。任何"因为 A 未接入，所以 B/C/D 都是模拟"的推论，一律不接受（对应 §7.5.4.2 规则 1）。

**真实用户操作边界（v1.3.2 新增独立条款）**：

1. 真实用户在 trial 中**只能**产生明确标记为 `simulated` 的演示操作（推进六阶段、模拟路线确认、模拟方向展示、重置自己 session）；
2. **不得**改变真实设备状态（`devices.status` / `direction` / `current_mode` 等）、真实告警状态（`alarms` 中非 `-DEMO` 行）、真实处置记录（`operation_logs` 中非 `SIM` 前缀行、`evacuation_plans` 中非 `DEMO-` 行）；
3. 上述"不得"必须在**服务端**落实（拒绝 + 审计），不能只靠前端禁用按钮；
4. 判定顺序固定为：`验签 → 查角色 → 判定目标行来源 → 拒绝或放行 → 写审计`；**先判来源后写数据**，不得先写后校验。

##### 7.5.4.2 六条强制规则

1. **trial 数据库是否包含真实业务数据，必须逐表、逐数据来源确认** —— 见 §7.5.4.3 核对表；任何"整库属模拟"的结论都不被接受；

#### 7.5.5 sessionId 为什么不能替代库级隔离（v1.3 明确）

1. `sessionId` 只决定 **DO 实例**（`idFromName(sessionId)`，`demo.ts:9-11`），控制的是**内存世界状态**；
2. 三张全局表**没有** session 列，写入后**无法按 session 过滤、无法按 session 清理**；
3. 即使未来补 `session_id` 列，也不能解决"E2E 的破坏性重放把 trial 数据改成测试态"的问题 —— 因为 E2E 会反复 `RESET` + `START_FIRE`，制造大量模拟告警与方案行；
4. 因此：**E2E 必须库级隔离（独立 test D1）；`sessionId` 只用于 DO 世界分片与审计归属**。二者不可互相替代。

##### 7.5.6.2 导出规则（四类来源，v1.3.3 新增）

| 来源 | 默认是否允许导出 | 最低权限 | 强制标记 | 计入 `origin_breakdown` |

| `real` | ✅ 允许 | `operator` | 无附加标记 | ✅ |

**`real` 的判定证据要求（v1.3.3，X-2）**：

| # | 规则 |
|---|---|
| R-1 | **合法写入权限 ≠ 真实来源证据**。任何角色（含 `admin`）通过 REST 写入的数据，**不得仅因"有权写"而标记 `real`** |
| R-2 | 只有具备**可信、可核验**的来源证据时才可写 `real`，例如：设备上报携带设备身份与批次/时序校验且可回溯到设备；批量导入携带工单号 + 源文件哈希；人工确认记录（含确认人 `sub` 与时间）。**证据必须独立于申报者**（v1.3.4，P2-4）：申报者**不得自行生成证据并自行证明**，证据须来自设备侧、外部工单系统或第三方留档 |
| R-3 | **无证据即 `unknown`**：宁可标为来源不明并按真实数据级保护，也不得标 `real`（宁严不宽） |
| R-4 | `real` 一旦写入，须保留证据引用（证据类型 + 标识 + 时间），供审计抽样核对。**过渡口径（v1.3.4，P2-5）**：migration 0003 未实施前，证据存放于**外部留档**（工单号 + 源文件 SHA256 + 审批记录），字段设计待 0003 议题确定 |
| **R-5a** | **申请人与审批人分离**：申请人（数据写入者或发现者）提交改判申请（含证据与影响行数）；审批人须为**不同 `actor_sub`** 的 `admin`；**禁止自申请、自审批**；同一主体不得同时出现在两侧 |
| **R-5b** | **批量改判约束**：单批上限、抽样复核比例、回滚窗口**均为拟议参数**（详见下方"拟议控制参数"），**未批准前不得作为安全标准引用**；超限须分批并逐批附证据清单 |
| **R-5c** | **三段留痕**：申请、审批、执行各自记录（主体、时间、依据、影响行数、结果），任一段缺失即视为未完成；反向改判（`real → unknown`）同样留痕 |
| **R-5d** | **能力声明（关键）**：申请单、审批链、权限点、审计端点**当前均不存在**（无表、无接口、无 UI）；因此 **`unknown → real` 在审批流实现前一律禁止**（Q2），**不得**以"admin 直接改"代替审批流；该机制属**未来代码实施项**，未获授权 |

##### 7.5.7.3 必须由服务端生成或校验的字段

1. `origin`：**禁止**客户端提交；**收到一律返回 400 并记审计**（v1.3.3 统一口径，不再保留"忽略"降级写法），服务端按路径判定；
2. `session_id`：**禁止**客户端提交（当前 `sessionId` 走 URL query，仅用于选择 DO；不得直接落库为行归属）；收到同样 400；
3. `actor_sub`：**禁止**从 `X-User` / `email` 头取；只从已验签 JWT 的 `sub` 取；客户端提交一律 400；
4. **写入顺序与失败语义（v1.3.3 更正，X-4）**：业务行与三个来源字段必须在**同一语句**内写入，不允许"先写数据后补标记"。**当前实现是多步写入且非事务（DB-004）**，因此：

   - **不得**声称已具备原子性或自动回滚；
   - 部分失败时，**必须保留失败状态与审计**（记录已写入的步骤、失败步骤、错误原因），**不得标记为"完整成功"**，也不得通过"补写标记"把失败行伪装成成功；
   - 真正的原子性修复（`batch()` / 事务语义 / 补偿）**属另行实施与验收的独立议题**，本轮不做、不承诺。

##### 7.5.7.4 历史数据迁移中"来源无法确定"的处理

| 情形 | 处理 | 理由 |
|---|---|---|
| 无法判断是真人操作还是演示产生 | `origin='unknown'`，`actor_sub='migrated'`，`session_id=NULL` | 不得默认视为 `simulated`（§7.5.4.2 规则 5） |
| 能确认由 Demo 产生（如 id 含 `-DEMO`、`module='演示流程'`） | 回填 `simulated`，并记录判定依据 | 命名证据可作为**弱证据**，须留审计说明 |
| 能确认由 seed 产生（id 匹配 `src/mock/*` 特征） | 回填 `test` | 同上 |
| 其余 | `unknown` + 进入人工复核清单 | fail-safe |

**迁移后必须产出**：`origin` 分布统计（各值行数）、`unknown` 清单、复核结论。`unknown` 占比未清零前，相关报表须显式标注"含来源不明数据"。

##### 7.5.7.5 四环责任关系（DB 约束 / 服务端写入 / 查询过滤 / 统计排除）

> v1.3.2 将原"三层（DB/应用/审计）"细化为**四环 + 一条旁路**：四个环节缺一，隔离即不成立；审计是横切能力，不替代任何一环。

| 环 | 负责 | 具体内容 | 不负责 |
|---|---|---|---|
| **R1 数据库约束** | 兜底"值域与存在性" | `CHECK(origin IN ('simulated','real','test','unknown'))`；`origin NOT NULL`；`actor_sub NOT NULL`；按 `origin` + `created_at` 建索引；迁移回填 `unknown` | 语义判定（"这次写入是否模拟"）、授权、过滤 |
| **R2 服务端写入逻辑** | 决定"每行到底是什么来源" | 按调用路径 + 命令类型 + 目标行判定 `origin`；**`real` 须有可信可核验证据（§7.5.7.2 R-1～R-5），仅"有写入权限"不得写 `real`**；生成 id/前缀/`module`/`type`；客户端提交标记一律 400；写入前做角色与来源双校验 | 长期对账、事后取证 |
| **R3 查询过滤** | 保证"读出来不混淆" | **白名单口径（v1.3.3 更正）**：真实业务视图 = `origin = 'real'`；`simulated` 仅演示视图；`test` 仅测试视图（默认不展示）；`unknown` **默认可见但强制标注**，且按真实数据级保护。**禁止使用 `origin != 'simulated'` 之类黑名单判定**（会把 `test`/`unknown` 当作真实数据）。WS 下发对象必须带来源字段 | 阻止写入、修正历史数据的错误标记 |
| **R4 统计排除** | 保证"算出来不失真" | **主 KPI 仅计 `origin = 'real'`**；`simulated` 与 `test` 排除；`unknown` **单列并标注"含来源不明数据"，不得计入达成率**；报表与导出同口径（§7.5.6.2）。**注：R4 的"排除"仅指统计口径，不等于删除或从审计中移除（§7.5.6.1）** | 展示层细节、权限控制 |
| **旁路 审计** | 事后可追溯 | 记录每次写入的 `origin`/`actor_sub`/判定依据；抽样对账；`unknown` 复核清单；异常检测（trial 出现 `real` 且无设备来源） | 实时拦截（不承担阻断职责） |

**来源口径定义（v1.3.3，四类来源的准入与可见性）**

| 来源 | 默认业务视图 | 真实业务 KPI | 默认导出 | 保护等级 | 关键约束 |
|---|---|---|---|---|---|
| `real` | ✅（需授权） | ✅ 唯一计入 | ✅（`operator+`） | 同生产 | 必须有可信可核验来源证据（§7.5.7.2 R-2） |
| `simulated` | ❌（仅演示视图） | ❌ | ❌ 需显式勾选，标"模拟演练" | 需标记与审计 | 不得伪装为 `real`；不得写入真实设备/告警 |
| `test` | ❌（仅测试视图） | ❌ | ❌ **默认禁止**，仅 `admin` 显式允许并标"测试数据" | 需标记与审计 | seed 专属；不得进入真实视图与 KPI |
| `unknown` | ✅ **但强制标注** | ❌（单列，不计达成率） | ✅ 需标"含来源不明数据"（`admin`） | **按 `real` 同级（fail-safe）** | **不得伪装为 `real`；不得进入模拟数据专用清理流程**（§7.5.6.1） |

> 三条绝对规则：①**`unknown` 既不是 `real` 也不是 `simulated`**，任何"非 real 即模拟""非 simulated 即真实"的二值化处理都禁止；②`test` 与 `simulated` 不得以任何形式进入真实业务视图与真实 KPI；③默认可见 ≠ 免授权，`unknown` 的读取仍需按数据敏感级别做访问控制（§3.5）。

**关键推论**：R1 通过不代表 R2 正确（字段存在但值错），R2 正确不代表 R3 生效（读路径仍全量返回），R3 生效不代表 R4 干净（KPI 若另算一遍仍会混入）。四环必须逐环验收。

##### 7.5.7.6 字段缺失或来源非法时的拒绝策略

| 场景 | 策略 |
|---|---|
| 写入时 `origin` 缺失 | **拒绝写入**（`422`），不接受 `NULL` 兜底；系统任务须显式传 `real`/`test` |
| `origin` 值不在枚举内 | DB `CHECK` 拒绝 + 应用层先返回 `400`（双保险） |
| 客户端提交 `origin`/`session_id`/`actor_sub` | **一律 `400`** 并记审计（视为探测行为）；**不设"忽略"降级路径**（v1.3.3 统一口径） |
| 读取到历史行缺 `origin` | 视为 `unknown` **正常返回但标注**，不得静默隐藏；导出时同样标注 |
| 迁移脚本无法判定 | 回填 `unknown`，禁止留 `NULL` |
| trial 库出现 `origin='real'` **且缺少可核验来源证据**（无设备上报 / 无导入工单 / 非授权内部任务） | 触发异常告警 + 人工复核（可能是错误标记或越权写入）；**有证据的 `real` 不判异常**（§7.5.7.2 R-2） |

##### 7.5.7.7 与门禁的关系（不因设计而放行）

- migration 0003 **未实施前**，§7.5.3 所有"未覆盖"项仍为未覆盖；G-04 / G-08 不得判 PASS；
- **仅增加数据库字段不会自动形成隔离**（v1.3.2 显式条款）：字段只是载体 —— 缺 R2 则字段永远为空或全填同一值；缺 R3 则读路径照样混展示；缺 R4 则 KPI 照样被污染；缺 R1 则可被绕过写入非法值。四环缺一，隔离即不成立；
- **`origin` 等字段属于 schema 变更，必须走独立 migration**（编号暂定 0003）：需单独评审、单独提交、单独回滚预案；**不得**夹带在功能提交或其他 migration 中；
- **RSK-11 继续保留为未解决**：字段设计只是方案，不等于已实现；且新增字段本身带来"迁移期双写不一致""unknown 比例未知""展示层过滤遗漏"等新风险；
- 本节内容**不得**被引用为"数据隔离已完成"的证据。

### 12.1 WS ticket 泄露面评估与替代方案比较（v1.2 新增，v1.3 调整结论：不预设排序）

**泄露成因**：WebSocket 握手是普通 HTTP GET，浏览器不允许为升级请求设置自定义头，因此票据只能放进 URL query 或 Cookie。放进 URL，就等于交给"所有记录 URL 的地方"。

**泄露面清单**：

| # | 面 | 是否记录 URL | 风险 | 说明 |
|---|---|---|---|---|
| 1 | Cloudflare 边缘请求日志（Workers / Pages） | **是（含 query）** | 高 | 保留期依 plan，**待核验**；具备日志权限者可批量收集 |
| 2 | 浏览器历史记录 | 否 | 无 | WebSocket URL 不进入历史 |
| 3 | `Referer` 头 | 否 | 无 | WS 握手不发送 Referer |
| 4 | 企业代理 / 网关 / 抓包 | 是 | 中 | 试用用户在企业网络下可被记录 |
| 5 | 前端错误上报 / 埋点 SDK | 可能 | 中 | 取决于是否把当前页面 URL 上报 |

**风险上限（必须写清）**：泄露的 ticket **不能调用任何 REST 接口**、**不能续期**、**只能升级一个 WS 并绑定一个 sessionId**。因此本质是"60 秒内的竞争使用窗口"，而非"长期凭证泄露"。

**替代方案比较**：

| 方案 | 机制 | 进 URL/日志 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|---|
| **A. 短时一次性 query ticket**（现行） | `POST /auth/ws-ticket` → `?ticket=` | 是 | 跨域无 Cookie 约束；可原子消费；实现最小 | 必然进日志；只能靠 TTL 压缩窗口 | 可用，须满足下方 5 条接受条件 |
| **B. HttpOnly Cookie** | 复用 `CF_Authorization` 或自签 HttpOnly Cookie | **否** | 不进 URL；JS 不可读；浏览器自动携带 | `SameSite=None; Secure` 带来 CSRF 面；要求 WS 与前端同站（`trial.x.com` / `api-trial.x.com` 可行）；Cookie 是**长期凭证**，泄露面从"日志"转为"自动携带 + CSRF" | **优先评估候选**（与 D 并列，不预设优劣；前置条件：同站部署 + CSRF 防护 + Cookie 生命周期收紧） |
| **C. `Sec-WebSocket-Protocol`** | 升级请求头携带子协议值 | 否（头不一定入日志） | 不进 URL；浏览器原生支持 | 子协议值受 token 语法限制；部分代理记录头；服务端须回选协议 | 可选备选 |
| **D. 首帧认证** | 连接后先发 `{type:'auth', ticket}`，认证前不发任何数据 | **否** | 无 URL 泄露（前提是严格执行"认证前不发任何帧"）；改造点集中在 DO | 须自建超时/限流/防重放；须改 `DemoRoom.ts:147-149`（当前连上即推全量快照）；实现不当会引入"空连接耗尽"与"先绑定后认证"两类新问题 | **优先评估候选**（与 B 并列，不预设优劣；前置条件见 §12.1.1） |

**残余风险接受条件（若保留方案 A，5 条缺一不可）**：

1. TTL ≤ 60s 且**一次性**（原子消费 `used_at IS NULL`，二次使用必拒）；
2. 票据仅授予"建立 WS + 绑定单 session"，**不得**具备任何 REST 调用能力；
3. 服务端只存 `SHA-256(ticket)`，不落明文、不入库明文、不打入应用日志；
4. 上线前实测：边缘日志保留期（按 plan）并**抽样检查日志样本**，确认 ticket 是否被截断/脱敏；若不满足 ≥7 天以内的控制，改用方案 B 或 D；
5. 试用期监控"同一 ticket hash 二次消费"，命中即告警并复核是否存在采集行为。

**v1.3 结论（取代 v1.2 的排序表述）**：

- **B（HttpOnly Cookie）与 D（首帧认证）并列为优先评估候选**，**不预设绝对安全排序** —— 二者的安全性取决于实现前置条件：B 的安全成立于"同站 + CSRF 防护 + Cookie 生命周期收紧"，D 的安全成立于"认证前零帧 + 超时关闭 + 限流 + 先认证后绑定"。任一前置条件缺失，二者都可能比 A 更差；
- **A（query ticket）不作为推荐方案**，仅在 B/D 均不可行时保留，且必须满足 §12.1 的 5 条接受条件；
- **C（子协议）** 保留为工程备选；
- 该比较**必须在 v1.4 前完成并留结论**，不得以"已接受 RSK-02"为由跳过。

### 12.1.1 首帧认证（方案 D）实现要求（v1.3 新增）

若最终选择 D，以下 5 条为**硬前置**，缺一即视为不可用：

| # | 要求 | 说明 / 现状对照 |
|---|---|---|
| D-1 | **认证前不发送任何快照与事件** | 当前 `DemoRoom.ts:147-149` 一旦 `acceptWebSocket()` 就立即 `send({type:'demo.snapshot', ...})`，**必须改造**：认证成功前只允许发送一条 `auth.challenge`（无业务数据） |
| D-2 | **未认证超时关闭** | ≤5s 内未收到合法 `auth` 帧即 `close(4401)`；超时定时器在认证成功后立即清除 |
| D-3 | **资源限制** | 单 DO 未认证连接数上限（建议 ≤20）；同一 IP/用户未认证连接上限（建议 ≤3）；单连接首帧大小上限（建议 ≤1KB）；超限即拒绝并计数 |
| D-4 | **认证成功后才绑定角色与 session** | 严格顺序 `验签 → 查角色 → 校验 session 归属 → 绑定`；**禁止**先按 URL 中的 `sessionId` 绑定世界、再认证（否则等于先给数据后验身份） |
| D-5 | **防重放与失败处理** | 首帧 `auth` 必须含 nonce + 一次性 ticket（复用 §3.3 票据，TTL ≤60s）；认证失败即关闭并计入失败计数，同一主体连续失败 ≥5 次触发限速；失败响应不含诊断信息 |

> 若选择 B，则对应的硬前置为：WS 与前端**同站**（同父域）、`SameSite=None; Secure`、独立 CSRF token、Cookie 有效期 ≤1h 且可服务端吊销。两条路线都必须在实现前写进契约（`API_CONTRACT.md`），不得口头约定。
