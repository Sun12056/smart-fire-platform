## 3. P0-01 root cause

**现象（B3-04 实测量）**

```
点选 PLAN-C：  fireStore.activeBuildingPlanId = 'PLAN-C'   ← View 直接写本地
              demoStore.selectedPlanId        = null
              demoStore.activeBuildingPlanId  = 'PLAN-A'（后端推荐）
确认：        backend activeBuildingPlanId    = 'PLAN-A'   ← UI 显示 PLAN-C，执行 PLAN-A
```

**根因两条：**
1. **两个可写意向槽**：`fireStore.activeBuildingPlanId`（本地预览）与 `demoStore.selectedPlanId`（Demo 面板选择）
   并存且互不同步；只有后者会被 `confirmEvacuationPlan → confirmRoute()` 读走。
2. **View 有直写权限**：`DashboardView.vue:628` 与 `RoutePlanView.vue:107` 直接调用
   `store.setActiveBuildingPlan()` —— 该路径**没有 Demo Guard**，即「View → 本地业务状态」链路。
   `setActiveBuildingPlan` 内部只改本地（`syncLegacyRouteState` + `applyRouteToDevices`（demo 下已被 B1 拦截）
   + `startEvacuationRun`（demo 下 `return true` 空转）），后端从头到尾不知道这次选择。

**为什么不能简单加 `demoGuard`**：现有回归会立刻失败。
`worker/e2e-phase2-browser.cjs:378/417` 与 `worker/e2e-phase2-consistency.cjs:384` 仍在 demo 模式下用
`store.setActiveBuildingPlan()` 做「同步切换方案并立即断言」，纯本地 API 是它们的前提；
「禁掉 + 保留本地差异」又会把双写留着，只是换个漏点。因此选择的是「**收敛到一个可写槽 + 单向投影**」。

## 4. P0-01 fix

唯一落点：**`demoStore.selectedPlanId`（Demo 模式下的操作员意向）**；
`fireStore / 2D / 3D` 全部是它的**投影**，不再有自己的意向写操作。

```text
View（DashboardView / RoutePlanView / DemoPanel）
  └─► store.selectBuildingPlan(id)                    ← View 层唯一入口
        ├─ demo：useDemoStore().selectPlan(id)        ← 唯一可写槽
        │        → WS 快照 / 阶段变化时由 bindPlanSelectionProjection()
        │          （watch { flush: 'sync' }）单向投影到 fireStore.activeBuildingPlanId
        │          → syncLegacyRouteState → 2D routePlans / 3D RouteLayer3D
        └─ mock/api：applyBuildingPlanSelection(id)   ← 保留原本地预览行为，一字未改
```

具体四点：

1. **新增 `selectBuildingPlan(planId)`**：demo 只写 `demoStore.selectedPlanId`；非 demo 走原本地预览。
   `setActiveBuildingPlan` 保留为**兼容入口**（历史调用方 / 既有 E2E 仍可用），但内部同样走这一个入口，
   不再出现「另一次本地写入」。
2. **新增 `bindPlanSelectionProjection()`**：`watch(demoStore.selectedPlanId, …, { flush: 'sync' })`
   → 调用内部 `applyBuildingPlanSelection(id)`（含 `syncLegacyRouteState`），保证选择**同步**驱动 2D/3D，
   不引入异步第二态。
3. **`applyBuildingPlans(snap)` 采纳意向**：`activeId = demoSelectedPlanId(plans) ?? snap.activeBuildingPlanId ?? recommended ?? plans[0].id`。
   即 **intent > executed**：选过就用「选的」，没选才用后端快照里的执行/推荐方案。
   因此 WS 重连 / 任何新快照都不会把已选意向打回推荐方案（T3 实测通过）。
4. **`demoStore.applySnapshot`**：后端 `buildingPlans` 为空（RESET / 新一轮演练前）→ `selectedPlanId = null`。
   意向的存在依附于后端下发的方案集合，不留上一次演练的残留。

**当前正式 View 入口已不再直接写 `fireStore.activeBuildingPlanId`**：`DashboardView` / `RoutePlanView`
的方案按钮都改走 `store.selectBuildingPlan()`；`setActiveBuildingPlan` 仍作为**兼容入口**存在
（历史调用方 / 既有 E2E 继续可用），但在 demo 模式下同样只写 `demoStore.selectedPlanId`，不再写第二份本地状态。
此外补齐一处漏口：`backToPlanList()` 原会把 `activeBuildingPlanId` 的值反向写回意向槽（fireStore → demoStore），
现已加 demo 守卫拦掉 —— demo 下意向槽只有「管理员点选」一个写入来源。

## 5. P1-01 root cause

`fireStore.applyDemoSnapshot` 对 persons / devices 是「按 id 合并」：

```js
const pmap = new Map(list.map(p => [String(p.id), p]))
persons.value.forEach(p => { const r = pmap.get(String(p.id)); if (!r) return; assignPersonRuntime(p, r) })
```

两个问题：

1. **只在「后端给了」的字段上写**：`assignPersonRuntime` 的注释明确写着
   「只写后端确实给了的字段，避免用默认值覆盖本地基线」——也就是说后端没给的
   `status / routeId / routePoints / progress / position / direction / emergencyFlash / currentMode / brightness`
   会继续保留**本地 seed 的值**，等于让 seed 反向补全了后端权威人员/设备的业务状态。
2. **没有成员边界**：本次后端运行时里**没有出现**的对象被原样跳过，上一轮 demo 留下的业务状态
   （`_evac` 本地疏散运行态、未清空的 `routeId / routePoints`…）可以长期挂在这些对象上。
   220 名人员里只有 89 名真正受 Demo 权威约束，其余 131 名既不是「静态结构」也不是「后端状态」，是不确定态。

## 6. P1-01 fix

在 fireStore 里把「Demo 模式下业务状态的唯一权威」显式化：

1. **成员边界**：每一轮 persons / devices 应用都以「本次后端运行时 id 集合」为边界。
   * 集合**内** → 走新的**整字段覆盖**（`applyStrictPersonRuntime` / `applyStrictDeviceRuntime`）：
     status / routeId / routePoints / progress / position / direction / emergencyFlash / currentMode / brightness
     一律取 `normalize*Runtime(source)` 的输出；后端没给的字段落**契约默认值**（`normal` / `[]` / `0` / `false`…），
     **不再用 seed 值补全**；`waypoint / route / movementType / evacuating / retained / rescued` 同理。
   * 集合**外** → `restoreBusinessSeed()` 还原到首轮记下的**非后端托管成员的初始恢复基线**
     （并清掉 `_evac / _evacDone`，不给 PersonLayer3D 的本地路线优先级留任何入口）。
     这份基线只在「本轮后端运行时没这个成员」时用于恢复初始外观，
     其中的 status / position 是**恢复基线**而非静态结构，**不参与任何业务判断**，
     也不会反向写回后端权威。
2. **canonical 不变**：merge 只写 `buildingId / floorId / zone`；
   `building / floor / area` 仍然只是派生展示字段，**没有重新成为业务权威**（B3-03 结论保持有效）。
3. **View 侧 ebenfalls**：`PersonView` 里「给该区域人员打 `status='warning'`」在 demo 模式下被拦（不反向写 store）；
   `DeviceView` 的第 661 行原本就有 demo 守卫，未改动。

### 8.2 关于 `worker/e2e-phase2-browser.cjs` 的两处改动（**请 review**）

本批修改后 **`test:e2e:browser` 曾出现 2 条失败**，分析如下：

| 失败断言 | 是否本批造成 | 分析 |
|---|---|---|
| `执行的是所选方案`（期望 `PLAN-B`，实际 `PLAN-A`） | 是 | 测试先点 DemoPanel chip 选 B（`selectedPlanId=B`），随后又用 `store.setActiveBuildingPlan()` 切到 A。旧语义下第二次操作**完全不进权威链路**，于是「第一次选择胜出」；新语义下**最后一次选择 = 意向**（唯一槽必然被覆盖），确认执行的自然是 A。**这恰好就是 P0-01 要消除的「两次选择不一致」。** |
| `2D/3D routeId 与后端人员 routeId 一致`（前端 PLAN-B vs 后端 PLAN-A） | 是 | 同一根因：确认后脚本用 `setActiveBuildingPlan('PLAN-B')` 恢复显示，旧语义下这只影响本地预览；新语义下它同时把**意向**改成 B，于是 UI 显示 B、后端已执行 A，该断言比较的正是这两者。 |

**处理方式**：未删除、未放宽任何断言，只把两处**流程步骤**对齐新语义 ——
1. 在切换方案后重新读取「即将确认的意向」：`confirmedPlanId = demoStore.selectedPlanId`，
   并用它做 `执行的是所选方案` 断言（断言强度不变：后端必须执行**当前所选**方案）；
2. 新增一条断言 `切换后意向槽与当前方案同源`（因此 95 → 96 条）；
3. 后面「恢复到最后点选的方案」由硬编码 `'PLAN-B'` 改为 `confirmedPlanId`（= 后端实际执行的方案），
   使后续几何/routeId 比对在「显示方案 = 执行方案」下进行。

如你判定这两处对齐不可接受，我可以还原这些步骤并单独汇报禁令冲突，但它们与 P0-01 的修复目标直接互斥。
