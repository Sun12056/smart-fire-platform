## 7. 路径算法

### 7.A 是否真正计算最短/最优路径？

**回答：是，真算法，不是固定 waypoint。**

- `dijkstra`（`routeGraph.js:226`）—— 标准 Dijkstra，支持封锁节点/边
- `kShortestPaths`（`routeGraph.js:277`）—— **Yen K 最短路**，k=3
- `pathCost`（`routeGraph.js:264`）—— 按图权重求和，跨层段额外 `+STAIR_DESCENT_M`
- 权重 = 欧氏距离 / `PX_PER_M(10)`（`routeGraph.js:159`）

**没有固定 waypoint、没有预设 routePoints、没有随机生成。**

### 7.B 是否考虑火灾区域？

**回答：考虑，但只在 2D 平面内，且有一条显式例外。**

`fireBlockSets`（`buildingEvacuationPlanner.js:81`）：

- 火源房间节点**必封**
- 若起点区域与火源**不同门厅** → 额外封锁火源门厅（火势蔓延走廊）
- 若起点区域与火源**同一门厅** → **不封门厅**（否则该区域唯一出路被堵死）
- 起点若恰是火源节点 → 从封锁集删除（"离开着火房间"不可避免）

实测（脚本 1 §6，火源 5F-A区）：

```
火源封锁节点: ["5F:A_CENTER","5F:CORRIDOR_N"]
PLAN-A 经过火源/火源门厅的路线节点:
   ["5F-A区 [0] 5F:A_CENTER", "5F-A区 [1] 5F:CORRIDOR_N", "5F-B区 [1] 5F:CORRIDOR_N"]
```

- `5F-A区` 是火源本身 → 起点豁免，合理
- `5F-B区` 与 A 区共用 `CORRIDOR_N` → 设计上豁免。**但这意味着 B 区人员要从着火的 A 区门口经过**，拓扑上 B 区只有这一条出路，算法无法避免
- 其余 22 个区域全部成功避开

### 7.C 是否考虑墙体（几何不可穿墙）？

**回答：有约束，且实测全通过；但约束的强度被拓扑本身和墙体模型的粗糙程度限制。**

`validateRoute`（`routeValidator.js:46`）四道防线：

1. 起点必须是 room/door，不能是 exit
2. 禁止 room→room 直连；跨层必须是 stair→stair
3. **必须是图中合法边**（`graph.adj[a].some(e => e.to === b.id)`）
4. **线段级几何校验**：`segIntersectsRect` 逐段与 `WALLS` 求交（`routeValidator.js:84`）

实测（脚本 1 §7）：

```
结论：全部路线通过 validateRoute（几何上不穿墙）
```

**但必须指出的三个削弱点：**

1. **拓扑先行**：因为路线只能走图上已有的边，而所有边（房间门口→走廊、走廊链、走廊→楼梯）在设计上就不穿墙，所以第 4 条几何校验**几乎永远不会触发**。它是"兜底"，不是主要保障。
2. **墙体只有 8 个矩形**：走廊南北墙、外墙、门洞都没建模，一条"贴着房间外边界走"的线不会被判穿墙。
3. **3D 渲染会平滑掉折线**：`RouteLayer3D.js:101` 用 `CatmullRomCurve3(pts, false, 'catmullrom', 0.35)`，在拐角处会**切角**，与通过校验的折线几何不完全一致（属渲染层偏差，P3）。

### 7.D 出口是否由算法决定？

**回答：是，且是动态决定的，没有任何 `A区→Exit1` 的硬编码映射。**

### 7.E 是否存在"所有人走同一出口"的问题？

**回答：存在，PLAN-C（安全优先）100% 单出口。**

```

PLAN-B  {"1F:EXIT_W":52,"1F:EXIT_E":39}  总人数=91
```

## 8. 火灾约束

### 8.1 场景 1：A 区火灾（5F-A区）

实测（脚本 1 §3 / §10）。以 PLAN-A（均衡）为例，5F 各区域去向：

| 火源 | 5F-A区 | 5F-B区 | 5F-C区 | 5F-D区 |
| --- | --- | --- | --- | --- |
| 5F-A区 | → EXIT_W（西） | → EXIT_E（东） | → EXIT_E（东） | → EXIT_W（西） |
| 5F-C区 | → EXIT_E（东） | → EXIT_W（西） | → EXIT_W（西） | → EXIT_E（东） |

观察：

1. **火源区 A 区走最近的西侧出口** —— 正确
2. **B 区（西侧）被派往东侧出口**，路径长度 63.3m / 58s，而它到西侧出口只需约 36m —— **负载均衡压过了距离**
3. **D 区（东侧）被派往西侧出口**（火源 5F-A区 时）—— 同样绕远
4. 出口分配**不是按区域的固定映射**，每次随策略与 `exitLoad` 变化

> 根因在 `pickRouteByStrategy`（`buildingEvacuationPlanner.js:145-151`）：
> ```js
> if (Math.abs(la - lb) >= 1) return la - lb   // 负载差 ≥1 人就直接选人少的出口
> return (b.score || 0) - (a.score || 0)
> ```
> 只要两出口人数差 ≥1，**完全忽略距离/风险/评分**。这在区域人数少时会强制制造"舍近求远"。

### 8.2 场景 2：出口被火灾阻断

**回答：业务上不支持。**

- 算法层（图节点删除）支持自动切换，实测 91 人全部改走另一个出口，`valid=true`
- 但**没有任何代码路径会让出口变为不可用**：`blockedNodesForFire` 不封锁出口，`EXIT_BLUEPRINTS` 无 `available` 字段，UI 也没有出口状态

### 8.3 场景 3：区域无法到达某出口，能否找第二出口

**回答：能。**

- `findPaths` 天然对**全部出口**求候选（`exitIdsOf(graph,'1F')`）
- `rankPlans` 的出口多样性轮转保证候选覆盖不同出口
- 实测 §8：每个区域都有通往**两个出口**的候选

### 8.4 【重大】风险指标不分层（跨层坐标别名）

**这是本次审计最重要的算法缺陷。**

`FLOOR_NODE_BLUEPRINTS` 在所有楼层使用**同一组 XY 坐标**。因此 `1F:A_CENTER`、`5F:A_CENTER`、`6F:A_CENTER` 的 XY 完全重合，均为 `(140,150)`。

而 `buildPlan` 计算 `fireDistance / escapeDistance` 用的是**纯 2D 欧氏距离**，完全不掺入层高：

```58:74:shared/evacuation/routePlanner.js
    const firePts = [...fireNodeIds].map((id) => graph.nodes[id]).filter(Boolean)
    points.forEach((p, i) => {
      if (i === 0) return
      firePts.forEach((f) => {
        const d = euclid(p, f) / PX_PER_M
        if (d < fireDistance) fireDistance = d
      })
    })
```

实测（脚本 3，火源 = 5F-A区）：

```
  1F-A区(火源下方 4 层) fireDistance=2m risk=HIGH
  5F-A区(火源同层)      fireDistance=2m risk=HIGH
  6F-A区(火源上方 1 层) fireDistance=2m risk=LOW
```

完整表（PLAN-A）：

| 区域 | 距火源(m) | 脱离距离(m) | 风险 | 与火源楼层差 |
| --- | --- | --- | --- | --- |
| 1F-A区 | 2 | 11 | HIGH | 4 |
| 2F-A区 | 2 | 35.8 | LOW | 3 |
| 3F-A区 | 2 | 35.8 | LOW | 2 |
| 4F-A区 | 2 | 35.8 | LOW | 1 |
| 5F-A区 | 2 | 14 | HIGH | 0 |
| 6F-A区 | 2 | 35.8 | LOW | 1 |
| 1F-C区 | 2 | 11 | HIGH | 4 |
| 5F-C区 | 27.6 | 35.8 | LOW | 0 |

**后果：**

1. `fireDistance` 几乎恒等于 2m（门厅到房间门口的距离），**完全失去意义**
2. `riskLevel` 出现**楼层倒挂**：1F（火源下方 4 层）判 HIGH，6F（火源上方 1 层）判 LOW
3. 汇总 `summary.riskLevel` 取最大值 → PLAN-A 整体被标 **HIGH**，直接污染 UI 风险展示
4. `SAFEST` 策略的排序键完全建立在这个失真指标上 → 直接导致 §7.E 的"91 人全挤东侧出口"

> 层高常量是存在的（`FLOOR_HEIGHT_M = 3.5`，`floorPlanData.js:417`），但**从未被用于风险距离计算**。


### 11.2 断点定位

**断点 = 第 ④ 层（`applyRouteToDevices`），并且按数据源模式分成两种断裂：**

#### 断点 A：`demo` 模式 —— 函数被 `demoGuard` 直接短路

```362:366:src/stores/fireStore.js
  function demoGuard(apiName) {
    if (!dataSource.isDemo) return false
    console.warn(`[fireStore] demo 模式禁止本地业务写入：${apiName}（请通过后端状态机 / WebSocket 快照驱动）`)

```

```
fireStore.js:3211   if (demoGuard('applyRouteToDevices')) return bindingsAcc || []
```

→ `routeDeviceBindings` 恒为 `[]`，**选 PLAN-A/B/C 完全不触碰任何灯的 direction**。
→ 后端也没有任何 route→light 逻辑（`worker/src` 中 `direction` 只出现在 `engine.ts:155` 的伪随机翻转与 `DemoRoom.ts:79` 的 D1 读取）。

> **demo 模式链路：方案已切换 ✅ → 路线已切换 ✅ → 灯方向零变化 ❌**

#### 断点 B：`mock` 模式 —— 函数执行了，但语义是"整层统一方向"

`applyRouteToDevices` 确实执行并写入 `d.direction`，但写入的是 `plan.exitSide` 派生的**整层统一值**（§10.3 / §10.4）。

> **mock 模式链路：方案已切换 ✅ → 路线已切换 ✅ → 灯方向被改写了，但改成了"整层同一个方向" ❌**
> 视觉结果：**切换 A/B/C 后，每层灯整体左/右翻转，但层内依旧完全同质 —— 用户感知为"没联动"或"联动得很假"**。

### 11.3 一句话结论

> **断点在第 ④ 层「route → light mapping」。**
> - demo 模式：`applyRouteToDevices` 被 `demoGuard` 短路（`fireStore.js:3211`），路线与灯**零绑定**；
> - mock 模式：绑定存在但只在"方案出口侧别"这一层（`fireStore.js:3225`），**没有路段级映射、没有逐灯方向计算**；
> - 无论哪种模式，`LightingView` 都不是链路的一环（它根本不处理 direction）。

### 13.2 核心判断：算法烂 vs mock 伪装

> **当前"算法很垃圾"的观感，成因是混合的，但必须分开看：**

**① 疏散路线本身 —— 是真算法，不是 mock 伪装。**

**② 指示灯方向 —— 是硬编码 + 随机伪装成"联动"。**

- `routeDeviceBindings` 这个"路线-设备绑定"结构看似业务产物，实际**无人消费**
- **这是"伪装成算法结果的 mock 数据"的典型：结构上有 routeId/deviceId/direction 三元组，语义上没有任何路段级映射**

**③ 火灾风险指标 —— 是真计算，但输入失真（跨层坐标别名），导致结果不可用。**

- 代码真的算了欧氏距离、真的查了 RISK_NEAR_M
- 但因为所有楼层共享 XY，`fireDistance` 恒等于 2m（§8.4）
- **是"算法正确但模型缺失维度"，不是 mock**

## 20. 最终结论

### Q1. 当前疏散算法真正入口是什么？

**两个入口，一个实现。**

- **demo**：`worker/src/demo/engine.ts:180`（`applyStageEffects` → `case 'ROUTE_PLANNING'`）
- **mock/api**：`src/stores/fireStore.js:2813`（`generateBuildingEvacuationPlans`）
- **统一实现**：`shared/evacuation/buildingEvacuationPlanner.js:268 planBuildingStrategies()`
  → 按 `BALANCED / FASTEST / SAFEST` 三策略各跑一次 `planBuildingEvacuation()`
  → 产出 `PLAN-A / PLAN-B / PLAN-C`

### Q2. 当前路线到底是不是算法计算出来的？

**是。**

Dijkstra（`routeGraph.js:226`）+ Yen K 最短路（`routeGraph.js:277`）+ 全出口候选（`routePlanner.js:127`）+ 出口多样性轮转（`routePlanner.js:165`）+ 不穿墙校验（`routeValidator.js:46`）。
**无预设 routePoints、无固定 waypoint、无随机生成。** 实测 24 区域 × 3 策略全部真实计算得出。

> 但路线的**选择策略**有问题（Q3 相关）：`pickRouteByStrategy` 的负载均衡阈值会压过距离，PLAN-C 因风险指标失真导致单出口。

### Q3. 当前有几个真正参与计算的安全出口？

**2 个。**

`1F:EXIT_W`（x=32,y=170,西侧）与 `1F:EXIT_E`（x=528,y=170,东侧），**都只在 1F**。
两者都是 `findPaths` 的真实目标（`exitIdsOf(graph,'1F')`），实测每个区域都能得到通往两个出口的候选 —— **出口已经参与算法，不是展示对象**。
但**没有可用性/容量建模**，火灾无法使任何出口不可用。

### Q4. A/B/C/D 是否拥有不同的出口分配？

**没有固定分配，是动态计算的；但结果常违反直觉。**

实测（火源 5F-A区，PLAN-A）：`A区→EXIT_W`、`B区→EXIT_E`、`C区→EXIT_E`、`D区→EXIT_W`。
换火源或换策略后立即改变（脚本 1 §10）。
**问题**：B 区在西侧却被派往东侧出口（63.3m，而西侧仅约 36m），D 区在东侧却被派往西侧 —— 原因是 `pickRouteByStrategy` 中"负载差 ≥1 人即换出口"直接压过了距离与评分。

### Q5. 当前路线是否具备真正的"不可穿墙"约束？

**有约束，且实测全部通过；但约束强度弱于字面含义。**

- 拓扑层：路线只能走图上存在的边，而边的设计本身不穿墙（主要保障）
- 几何层：`validateRoute` 用 `segIntersectsRect` 逐段与 `WALLS` 求交（兜底）
- 实测：24 区域 × 3 策略 = 72 条路线**全部通过** `validateRoute`

**但**：`WALLS` 只有 8 个矩形（4 房间 + 4 隔墙），走廊南北墙、外墙、门洞**未建模**； rooms 被压缩成门口单点，房间内部无路径。因此几何校验"几乎不会触发"，它是兜底而非主要保障。

### Q6. 当前路线是否真正避开火灾区域？

**平面上避开了；但不分层，且有一条显式豁免。**

- 火源房间必封，不同门厅区域额外封火源门厅（`fireBlockSets`）
- 实测 22/24 个区域完全避开
- **例外**：`5F-B区` 与火源 A 区共用 `CORRIDOR_N`，代码显式不封（否则 B 区无路可走）→ B 区人员必经火源门厅
- **重大缺陷**：风险距离用纯 2D XY，所有楼层节点 XY 重合 → `fireDistance` 恒为 2m，1F（火源下 4 层）判 HIGH、6F（上 1 层）判 LOW，**楼层倒挂**

### Q7. 人员移动是否使用同一份 canonical route？

**NO —— 同源但不等价。**

- 2D 路线 vs 3D 路线：**YES**，同一 `activeBuildingPlan.routes[i]`
- demo 人员路线 vs 2D/3D：**YES**，同一 `route.points`，同一 `routeId`
- **mock 人员路线 vs 2D/3D：NO**。`startEvacuationRun` 只保留本层 corridor/stair 节点（`fireStore.js:1337-1344`），丢弃跨层下行段与出口节点；且 `p.routePoints` 恒为 `[]`
- 人员**不自己重算路线**（`PersonLayer3D.js:165` 明确"3D 绝不自己算路线"）

### Q8. 疏散指示灯方向由谁决定？

**由硬编码 + 伪随机决定，与路线无关。**

| 阶段 | 决定者 | 位置 |
| --- | --- | --- |
| 初始 | 硬编码 `x < 280 ? 'left' : 'right'` | `floorPlanData.js:205/246` |
| demo 应急 | **伪随机 `rand() > 0.5` 翻转**（与火源位置无关，注释还写错） | `engine.ts:155` |
| mock 应急 | 距火源门 ≤110px 且"朝向火源"则翻转（两处重复实现） | `fireStore.js:1100` / `:1768` |
| "路线联动" | `plan.exitSide`（终点是否东出口）→ 整层统一 | `fireStore.js:3225` |
| 人工 | 管理员点选 / 批量 | `fireStore.js:2294` / `:854` |

**不存在 `Route → Route Segment → Light → Direction` 链。当前路线与指示灯方向不存在业务级绑定。**

### Q9. 确认疏散方案后，路线和指示灯为什么没有形成联动？

**断点在第 4 层「route → light mapping」，按模式分两种断裂：**

```
① 用户选择 PLAN-A                     ✅ 通  selectBuildingPlan (fireStore.js:2935)
② activeBuildingPlan 更新             ✅ 通  applyBuildingPlanSelection (:2912)
③ canonical route 切换                ✅ 通  syncLegacyRouteState (:2769)
④ route → light mapping               ❌ 断
⑤ direction update                    ❌ 断
```

- **demo 模式（断点 A）**：`applyRouteToDevices` 第 3211 行被 `demoGuard` **直接短路返回空数组** → 方案切换对灯零影响；后端 `worker/src` 也不存在任何 route→light 逻辑
- **mock 模式（断点 B）**：绑定执行了，但方向只来自 `plan.exitSide` 一个标量，且按 `floorsPassed` **整层覆写、后写覆盖先写** → 每层所有灯 100% 同向（实测 1F/2F/6F 全 right，3F/4F/5F 全 left）。用户看到的是"整层一起翻转"，感知上等同于"没有真正的联动"
- **共同点**：`routeDeviceBindings` 生成后**无任何消费者**；`LightingView` 全文件无 `direction` / `route` 引用，不在链路上

### Q10. 进入 P1.8-01 / P1.8-02，哪些必须重构，哪些可以直接复用？

**必须重构（17 项，见 §17）**，核心是三条：

1. **数据模型**：拓扑加"层"维度（R-1）、出口加可用性/容量（R-2）、墙体模型扩展（R-3）、删除第二套死拓扑（R-4）、建立真正的 route↔light 映射模型（R-5）
2. **算法**：修复分层风险指标（R-6/R-7）、修正负载均衡压过距离的选择策略（R-6）、重新设计共用门厅拓扑（R-8）
3. **联动**：重建 route→light direction 整条链（R-9/R-10/R-11/R-12），统一 mock/demo 人员路线（R-13/R-15）

**可直接复用（17 项，见 §18）**，核心是：

- **图基建**（`buildBuildingGraph` / `nodeId` / `euclid`）—— K-1
- **Dijkstra + Yen K 最短路** —— K-2
- **`validateRoute` 四道校验框架** —— K-3
- **`findPaths` 全出口骨架 + `rankPlans` 出口多样性** —— K-4/K-5
- **整栋楼三策略框架 + `BuildingEvacuationPlan` 数据结构** —— K-6/K-9
- **`fireBlockSets` 动态障碍机制** —— K-8
- **后端 `route → person.routeId/routePoints` + `tickWorld`** —— K-11/K-12
- **2D/3D 三端同源消费 + `activeBuildingPlan` 订阅** —— K-13/K-14
- **设备运行态统一契约的读侧** —— K-15
- **420 项现有单元测试作为回归基线** —— K-16

> **总体判断**：疏散**路径计算**的地基是好的（真图、真算法、真校验、真多出口），问题集中在「风险模型缺层维度」与「路线→灯的映射层根本不存在」。P1.8-01/02 应当**保地基、建映射、修指标**，而不是重写寻路。
