## 二、删除 / 废弃的旧逻辑

1. **`world.plans` 作为业务决策源** —— 废弃。改名为 `legacyPlans`，只用于 D1 历史与旧 REST 兼容；快照字段名仍为 `plans/activePlanId`（兼容前端旧字段），但语义为 LEGACY。
2. **CONFIRM_ROUTE 的旧门禁** `!world.plans.length` + `planId` 匹配 —— 删除；改为必须携带 `buildingPlanId`，并校验 `scope=BUILDING`、`buildingId` 一致、全楼有人区域路线合法。
3. **阶段4 用旧 zone plan 补路线** —— 删除（原 `p.route = plan ? plan.nodes : []` 回退分支移除）。
4. **旧接口混入整栋楼方案** —— 停止：`/api/v1/evacuation-plans` 不再返回 `type='building'` 行。
5. **`routeMatrix.perZone` 的业务用途** —— 废弃为只读投影：`applyFireBlocking` / `replanRoutesForFire` / `setCurrentRoutePlan`（legacy 分支）/ `currentRoutePlan`（legacy 分支）均只在无整栋楼方案时生效。
6. **UI 旧语义** —— 删除「A/B/C/D 四区分组方案」「本区域推荐/备用路线」「该区域最快/最安全路线」以及 2D 备用路线虚线（A/B/C 是三套整栋楼策略，不是同一区域的三条路线）。

## 三、buildingPlans 数据流

```
火灾发生（fireEvent 只描述位置：buildingId B003 / 5F / A区）
        ↓ evacuationScope = BUILDING（恒）
buildingEvacuationPlanner.planBuildingStrategies
  ① groupPersonsByZone（整栋楼人员，按 floorId+zone；走廊 → resolvePlanningZone 归并）
  ② 每组调用既有 findPaths()（Dijkstra / Yen 未改）
  ③ pickRouteByStrategy（A 均衡+出口负载均衡 / B 快速 / C 安全）
  ④ validateRoute 逐条校验（不穿墙、不经火区、终点 1F:EXIT_*、跨层必经楼梯）
        ↓
BuildingEvacuationPlan × 3（PLAN-A/B/C）   ← 唯一权威
        ↓  落库 evacuation_plans(type='building')
   Worker snapshot: buildingPlans / activeBuildingPlanId / evacuationScope
        ↓  WebSocket 广播
   fireStore.buildingEvacuationPlans / activeBuildingPlanId
        ↓  单向投影（syncLegacyRouteState）
   routePlans / routeMatrix.perZone / activeRoutePlanId（只读兼容，供旧组件与当前楼层展示）
        ↓
   2D RouteLayer(getAllZoneRoutes) · 3D RouteLayer3D · PersonLayer3D · 后端人员移动
```

## 四、activeBuildingPlanId 数据流

```
阶段3：DemoPanel 点选 PLAN-A/B/C → demoStore.selectedPlanId
        ↓ CONFIRM_ROUTE { buildingPlanId }
    DemoRoom 校验（scope / buildingId / 全楼路线覆盖）
        ↓ applyStageEffects(SMART_EVACUATION)
    world.activeBuildingPlanId = PLAN-B（唯一）
        ↓ 整栋楼每人 routeId = `PLAN-B:${floorId}:${zone}`、routePoints = 该路线点列
        ↓ snapshot / WS
    fireStore.activeBuildingPlanId → activeBuildingPlan（computed）
        ↓
    2D/3D/人员运动全部按该方案；切换 → setActiveBuildingPlan → 全楼重绑
```

**唯一性**：`resolveBuildingPlan` 只接受 `buildingPlans` 内的 id；`activeBuildingPlanId` 是唯一当前方案，
`legacyActivePlanId` 只是历史镜像，绝不反向写入。

## 七、发现但暂不处理的 TODO

1. **禁用楼梯未迁移**：`FLOOR_CONFIG.stairsActive`（3F/4F/6F）在 shared 拓扑中无对应；需要 shared 增加 per-floor 楼梯黑名单（本次按约束未动）。
2. **走廊人员起点语义**：用 `resolvePlanningZone`（按最近房间节点归并）近似，不是真实走廊语义；建议在 routeGraph 增加走廊起点节点后替换。
3. **`DeviceRuntime` 快照不含 floorId**：demo 快照的设备对象没有楼层字段，前端无法按楼层统计联动结果（后端确为整栋楼联动：136 台 ≈ 全楼 138）。可在快照补 `floorId`。
4. **P2 滞留人员候选**：仍为 `unfinished.slice(0,2)` 随机取 2 人 + 火源区兜底；演练中出现「已完成撤离的人员被兜底标记为滞留」的现象（已调整 E2E 断言为稳态不变量「位置冻结」，未改 P2 逻辑）。
5. **旧字段命名**：快照仍下发 `plans/activePlanId`（LEGACY 兼容）。若确认前端无消费方，可移除这两个字段。
6. **`evacuationPlanService`（src/api）无调用方**：保留未删，后续可直接删除或改指向新接口。
