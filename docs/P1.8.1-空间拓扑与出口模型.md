## 2. 新拓扑模型：唯一权威源

新增 `shared/evacuation/floorTopology.js` 作为**唯一权威拓扑数据源**：

```
楼层 → 区域 Zone → 走廊 Corridor → 拓扑节点 Node → 可通行边 Edge → 楼梯 Stair → 安全出口 Exit
```

三文件分工：

| 文件 | 职责 | 是否含算法 |
| --- | --- | --- |
| `floorTopology.js` | 拓扑数据 + 纯查询（节点/边/墙体/区域/楼梯/出口/楼梯可用状态） | 否 |
| `topologyGraphAdapter.js` | 拓扑 → `{nodes, adj}` 图；边实体视图；`validateTopology()` 自检 | 否（只翻译） |
| `topologyReachability.js` | Zone → Exit 三态可达性 | 否（只判可达，不评分） |

**未新增第三套数据**：墙体只有 `floorTopology.WALLS` 一份；楼层几何仍用 `floorPlanData` 的 SVG 560×300 坐标；`routeValidator` 的几何规则原样复用。

## 3. Node 定义

```js
{ id, floorId, key, x, y, type, zone, label, side }
```

- `id = \`${floorId}:${key}\`` —— 跨楼层唯一
- `type` ∈ `ROOM`（房间门口）/ `CORRIDOR`（走廊节点）/ `STAIR`（楼梯间）/ `EXIT`（安全出口）
- 单层 13 个：4 房间门口 + 5 走廊 + 4 楼梯；出口仅 1F 追加 2 个
- 整栋图节点数 = 楼层数 × 13 + 2（契约保持，见 §10 T8）

房间疏散起点取**门口**而非几何中心：房间只有经门才能进入走廊，从结构上避免"路线第一段从房间内部穿出"。

---

## 4. Edge 定义

```js
{ id, from, to, type, floorId, distance, walkable, blocked }
```

- `id = edgeKey(from, to) = sorted(from,to).join('|')` —— 与既有 `blockedEdges` 口径一致
- `distance`：由坐标推导（平面 `euclid/PX_PER_M`，跨层 `STAIR_DESCENT_M = 6`），**不手写**，避免与坐标脱节
- `type` ∈ `room_door` / `corridor` / `stair_access` / `stair_descent` / `exit_access`
- `walkable`：拓扑层面可通行；`blocked`：由火灾阻断层写入

邻接项在既有 `{ to, w, ek }` 基础上**追加** `t`（边类型）。既有读取方只读 `to/w/ek`，不受影响。

## 5. Zone 与拓扑关系

```js
ZONE_DEFS = [
  { zone:'A区', doorKey:'A_CENTER', hallKey:'CORRIDOR_N' },
  { zone:'B区', doorKey:'B_CENTER', hallKey:'CORRIDOR_W' },
  { zone:'C区', doorKey:'C_CENTER', hallKey:'CORRIDOR_S' },
  { zone:'D区', doorKey:'D_CENTER', hallKey:'CORRIDOR_E' },
]
```

### D3 共门厅修正（原 P1.8.0 F-18）

**原问题**：A/B 共用 `CORRIDOR_N`、C/D 共用 `CORRIDOR_S`。火源门厅既是火势蔓延封锁点，又是邻接区唯一出口通道 —— 封则邻接区困死，不封则邻接区必须贴着火源房间门口通过。

**修正**：四区声明**互不相同**的 `hallKey`，并为 B/D 增加通往远端门厅的备选边。

**为什么不是"直接把 B/D 改接到远端门厅"**（曾实现过，实测后回退）：

| 方案 | D 区西行距离（1F） | D 区东行 | 结论 |
| --- | --- | --- | --- |
| 直接改接 D→`CORRIDOR_E` | 40.3 → **51.0** | 10.8 | 门在 x=415 却被迫先向东到 x=477 再折返，**+10.7m 劣化** |
| **保留近端边 + 增远端备选边**（采用） | 40.3 → **40.3** | 10.8 | 无劣化，且门厅被封时仍有备份通路 |

`hallKey` 语义已明确为：**仅用于火灾蔓延封锁判定**（`routePlanner` 的 `startHall/fireHall`、`buildingEvacuationPlanner.fireBlockSets`），不表示"几何最近门厅"。

## 6. Stair 模型（D2）

```js
STAIR_DEFS = [
  { key:'STAIR_NW', planStairId:'S-A', ... },
  { key:'STAIR_NE', planStairId:'S-B', ... },
  { key:'STAIR_SW', planStairId:'S-C', ... },
  { key:'STAIR_SE', planStairId:'S-D', ... },
]
STAIR_ACTIVE_FLOORS = {
  '1F': 全部4部, '2F': 全部4部,
  '3F': [NW, NE, SW],  // S-D 停用
  '4F': [NW, NE, SE],  // S-C 停用
  '5F': 全部4部,
  '6F': [NE, SW, SE],  // S-A 停用
}
```

**决策 D2=B 的落地方式**：
- 楼梯**节点保留**（全楼层 13 节点契约不变，节点数不减少）
- 停用只影响**跨层下降边是否进入图**：仅当楼梯在上下两层都可用时才生成该跨层边
- 跨层边总数 = 15（若全可用则为 20）
- 2D 渲染侧 `floorPlanData.activeStairsForFloor()` 改为反向取同一份状态 —— **消除"2D 停用、算法照走"的分叉**

`planStairId` 把算法楼梯与 `floorPlanData.STAIRS[].id` 对齐，保证"画哪些楼梯"与"能走哪些楼梯"同源。

## 7. Exit 模型（D1 = A：不扩数量）

真实安全出口仍为 **2 个、均在 1F**。不为了模型完整凭空增加建筑出口。

```js
{
  id:'EXIT_W', key:'EXIT_W', buildingId:null, floorId:'1F', nodeId:'1F:EXIT_W',
  type:'EXIT', label:'西侧安全出口', side:'left', x:32, y:170,
  available:true, status:'OPEN', capacity:null,
}
```

| 字段 | 说明 |
| --- | --- |
| `floorId` / `nodeId` | 回答「出口在哪里、连接哪个拓扑节点」 |
| `available` / `status` | 回答「当前是否可用」；`status` ∈ `OPEN` / `CLOSED` / `BLOCKED` |
| `capacity` | 容量上限；**当前无业务消费**，P1.8.2 容量约束启用前保持 `null` |
| `buildingId` | 拓扑与楼栋无关（同一平面模型被多栋楼复用），楼栋归属由运行态决定，故为 `null` —— 与任务书原型 `{ id, buildingId, floorId, nodeId, type, available }` 的**唯一偏差**，已在此显式记录 |

出口从"UI 图标"升级为**可参与路径约束的实体**：`findPaths` 的候选目标默认过滤掉不可用出口。

## 8. 火灾阻断模型

`fireBlockSets` 返回值扩展（向后兼容，原 `blockedNodes` / `fireNodeIds` 不变）：

```js
{ blockedNodes, blockedEdges, fireNodeIds, exits }
```

| 层 | 机制 |
| --- | --- |
| 节点 | 火源房间 +（火势蔓延时）火源门厅；起点豁免（火源区人员仍需撤离） |
| 边 | `blockedEdgesForFire()`：任一端落在封锁节点上的边即被切断，供 Dijkstra / Yen 消费 |
| 出口 | 出口实体状态可在 `fireBlockSets` 中被改写为 `BLOCKED` —— **通用机制已接通下游** |

### ⚠️ 两种语义必须区分（P1.8.1 收口复核明确）

| 语义 | 是否实现 | 说明 |
| --- | --- | --- |
| (a) 出口节点被**通用阻断机制**封锁 | ✅ 机制存在 | `fireBlockSets` 中若出口节点出现在 `blockedNodes`，其实体状态同步为 `available:false / status:BLOCKED`；`findPaths` 随即不再把它作为候选目标 |
| (b) **火灾逻辑自动识别**出口不可用 | ❌ **尚未实现** | `blockedNodesForFire` 只产出 `ZONE_NODE_KEY`（房间门口）与 `ZONE_CORRIDOR_KEY`（门厅），**从不产出出口节点** |

因此：**当前火灾规则下 (a) 分支永远走不到 —— 火灾不会直接导致出口不可用**。这不是缺陷，而是本批次的明确边界（出口不可用目前只能由运行态显式传入 `exits` 数组）。一旦 P1.8.2 扩展 `fireBlockSets` 使其封锁出口节点，(a) 分支自动生效，下游 `findPaths` / `rankPlans` 无需改动。

**出口不可用的三条触发路径**（均经 `isExitUsable` 单一谓词判定，已由测试覆盖）：
`available=false` / `status=CLOSED` / `status=BLOCKED`。

### `findPaths` 出口过滤契约（二次复核明确，未改公共接口）

| 入参 | 语义 | 行为 |
| --- | --- | --- |
| 不传 `exits` | 默认 | 回落 `EXIT_DEFS`（两出口均 `available:true/OPEN`）→ **旧调用方零影响** |
| 完整 `exits` 数组 | 状态覆盖 | 被关闭/阻断的出口不进入候选目标 |
| **部分** `exits` 数组 | 状态覆盖（**非白名单**） | 未列出的出口回落 `EXIT_DEFS` 默认状态；已列出的不可用出口仍被排除 |
| `exits: []` / `exits: null` | 无覆盖 | 回落默认，不崩、不误杀 |
| `exitIds` | **白名单**（唯一候选裁剪手段） | 只从指定出口选路；若指定的是已关闭出口，结果为空，**不静默改走其他出口** |

> 说明：`exits` 与 `exitIds` 的语义边界在本批次显式固定为「状态覆盖 vs 候选白名单」。**未改变 `findPaths` 公共接口签名**，仅补测试固化行为。

### 合并顺序（二次复核修正项）

```
EXIT_DEFS（静态默认）
   ↓ 作为 baseExits 传入
fireBlockSets(..., baseExits)  ── 只叠加火灾 BLOCKED，不回退运行态 available/status
   ↓
findPaths({ exits })           ── 单一谓词 isExitUsable 过滤
   ↓
候选目标
```

**修正前缺陷**：`fireBlockSets` / `planZoneRoutes` / `planBuildingEvacuation` 均无运行态 `exits` 入口，运行态维护性关闭（`CLOSED`）与人工阻断（`BLOCKED`）在进入规划链时被静默丢弃，只有绕过规划链直调 `findPaths` 才生效。

**修正方式**（向后兼容，仅新增可选参数，默认值不变）：
`fireBlockSets(graph, fire, floorId, zone, startId, baseExits = EXIT_DEFS)`；
`planZoneRoutes({ ..., exits })`；`planBuildingEvacuation({ ..., exits })`。
修正后运行态状态可穿透整条规划链；不传时行为与修正前逐字节一致（已有测试固化）。

## 9. 与现有 Graph / Dijkstra / Yen 的关系

**未重写任何算法**，采取"拓扑 → Adapter → 现有算法"：

```
floorTopology.js（唯一权威数据）
        ↓
topologyGraphAdapter.js（翻译）
        ↓
{ nodes, adj } —— 结构与 P1.8.1 之前完全一致
        ↓
既有 dijkstra / kShortestPaths / findPaths / rankPlans / validateRoute
```

- `dijkstra`、`kShortestPaths`、`pathCost`、`riskByFireDistance`、`rankPlans` **函数体逐字未改**
- `routeValidator.js` 的 `segIntersectsRect` / `segSeg` / `validateRoute` **几何规则未改**；仅把 `edgeKey`/`WALLS` 的 import 源从 `routeGraph` 改为 `floorTopology`（避免循环依赖）
- `routeGraph.js` 保留全部既有导出（含 `FLOOR_NODE_BLUEPRINTS` 等蓝图常量），旧 import 不断

## 12. 已知限制

1. **出口仅 2 个且都在 1F**（D1 决策）—— 因此各区候选出口集合仍完全相同，"不同区域拥有不同候选出口集合"在当前建筑数据下无法体现差异化；需在建筑数据层面增加出口才能验证。P1.8.2 的分配策略需据此设计。
2. **B/D 房间节点度为 2**（近端门厅 + 远端备选门厅）—— 语义上是"门口开向连续走廊带，可连接走廊上多个 waypoint"（与 `CORRIDOR_N` 同时接 `CORRIDOR_W`/`CORRIDOR_CENTER` 同理），不是"房间有两个门"。A/C 仍保持度为 1。
3. **`hallKey` 语义**：用于火灾蔓延封锁判定，不等于几何最近门厅。B 区 `hallKey` 为 `CORRIDOR_W`，因此 B 区起火时会封锁西端楼梯厅 —— 属**保守过度封锁**（安全侧误差），已记录。
4. **火灾仍不直接封锁出口**（语义澄清，非缺陷）：见 §8 的两种语义区分。`blockedNodesForFire` 只封锁房间门口与门厅节点，从不产出出口节点，因此**火灾逻辑不会自动使出口不可用**；`fireBlockSets` 中"出口节点被封锁 → 状态置 BLOCKED"的**通用机制存在且已接通下游**，只是当前业务规则触发不到。出口不可用目前只能由运行态显式传入 `exits` 数组。
5. **`capacity` 为 `null` 的语义 = 「容量未知 / 未配置」**，**不等于无限容量**。当前不执行任何容量约束，也无任何代码读取 `exit.capacity`；P1.8.2 启用容量模型前保持 `null`。
6. **无几何意义上的"房间内部"建模**：房间只有门口节点，路线不进入房间内部，因此"路线穿房间"在几何上不可能发生，但也无法表达房间内的路径细分。
7. **走廊仍为 1D 链**：走廊是连续带（y=150~190），当前用 5 个中心线节点离散化，无法表达"贴北侧行走"等横向避让。
8. **运行态出口状态尚无生产调用方**：`planBuildingEvacuation` / `planZoneRoutes` / `fireBlockSets` 现已支持传入运行态 `exits`，但仓库内**没有任何生产代码调用它**（`fireStore` 等仍走默认 `EXIT_DEFS`）。能力已就绪、待 P1.8.2 或后续阶段接入真实出口状态源（如人工关闭、容量超限、外部告警）。
9. **路线消费者未按统一口径收敛（留给后续「路线消费者统一」工作的输入）**：本批次刻意未改动任何消费方，因此出现**两条并存的路线产出路径**，其出口约束口径并不一致：

   | 路径 | 产出 | 入口是否接收运行态 `exits` | 出口过滤是否生效 |
   | --- | --- | --- | --- |
   | 整栋楼方案 | `planBuildingEvacuation` / `planZoneRoutes` | ✅ 接收 `exits` | ✅ 生效（§16 R3/R4 已验证） |
   | Demo Engine `legacyPlans` | `planEvacuationRoutes`（`routePlanner.js`） | ❌ **不接收 `exits`** | ❌ 恒走默认 `EXIT_DEFS` |

   - 根因：`planEvacuationRoutes` 内部调用 `findPaths` 时未转发 `exits`，故 `findPaths` 回落到默认参数 `EXIT_DEFS`。
   - 现状影响：`legacyPlans` 仅写入 `world.legacyPlans`（历史/旧接口），按 P1.7 既定结论**不作为任何决策依据**，因此当前**无安全风险、无行为回归**。
   - 待办输入：后续「路线消费者统一」工作应决定 `legacyPlans` 的处置（收敛到整栋楼方案 / 补齐 `exits` 透传 / 随旧接口一并下线），使**所有路线消费路径的出口约束口径统一**；在此之前，任一对 `legacyPlans` 的消费都不得假设出口过滤已生效。
