### 2.2 入口与目标设备筛选（`fireStore.js:4134-4146`）

```4134:4146:src/stores/fireStore.js
  function applyRoutesToDevices(routes, bindingsAcc) {
    const list = (routes || []).filter(Boolean)
    if (!list.length) return bindingsAcc
    const buildingKey = list[0].buildingId || list[0].buildingName
    const floorsPassed = [...new Set(list.flatMap((r) => r.floorsPassed || []))]
    const targets = asArray(devices.value).filter(
      (d) =>
        d &&
        deviceInBuilding(d, buildingKey) &&
        floorsPassed.includes(floorIdOf(d)) &&
        (d.type === 'evacuation_light' || d.type === 'emergency_light'),
    )
```

**已证实的事实（非缺陷推断，是行为描述）：**

1. **楼栋归属只取 `list[0]`**：若一次传入混合楼栋的路线，全部设备按第一条路线的楼栋过滤（`:4137`）。当前生产调用方均单楼栋 ⇒ 尚未触发。
2. **`floorsPassed` 是本次入参路线的并集**（`:4138`）。传入几条路线，覆盖范围就是几条路线的途经楼层之和。
   - 整栋楼入口传入全部路线 ⇒ 覆盖全楼途经楼层。
   - **单路线入口（`:4087`、`:1906`、`:3098`）只传入 1 条路线** ⇒ 覆盖口径随之收窄为「这一条路线的途经楼层」。
3. **筛选条件只有「楼栋 + 楼层 + 类型」三项**，不含：
   - 设备通信状态 `d.communication`（`online` / `offline`）
   - 设备距路线的远近（距离在裁决阶段才计算，**不作为准入条件**）
   - 设备 `status`（`normal` / `fault`）

⇒ **结论（已证实）**：目标设备的准入与「几何上是否真的属于这条路」无关，也与设备是否在线无关。

## 3. 多路线覆盖与冲突绑定分析

### 3.1 路线顺序覆盖：**已被消除**（已证实）

旧缺陷（逐条 `forEach(route => applyRouteToDevices(route))`，后一条覆盖前一条）在
`shared/evacuation/deviceDirection.js:1-22` 的模块说明中有记载。当前实现：

- `applyBuildingRoutesToDevices` 一次性把**全部**路线交给 `resolveDeviceDirections`（`fireStore.js:4105-4118`）；
- `shared/evacuation/deviceDirection.js:287-376` 的裁决算法先收集**所有路线**对该设备的候选，再统一裁决；
- `shared/evacuation/deviceDirection.js:4202-4212` 只写 `bindings` 里的设备，且 `bindings` 中 `deviceId` 天然唯一（`deviceDirection.js:365-372`，每台设备只 push 一次）。

⇒ **结论**：**不存在**「后处理循环覆盖前一条路线写入方向」的问题。每条差异化责任在 `deviceDirection.js:9-16` 有明确设计约束并在代码中兑现。

### 3.2 是否用人数 / 字典序等非权威规则裁决：**否**（已证实）

- `weight` 传递：`fireStore.js:4159`
  `list.map((r) => ({ id: r.id, path: r.path, weight: r.congestion ?? r.personCount ?? null }))`
  注释明确「weight 只作为诊断信息进入 conflicts.candidates，不参与方向裁决」。
- 读取函数 `deviceDirection.js:77-81` `routeLoadOf()` 的产出只落到 `candidates[].load`（`:309`、`:345`）。
- **`routeId` 字典序的使用位置唯一**：`deviceDirection.js:321-328`，且注释明确「字典序**只**用于 ② 之后的稳定排序（保证正序/逆序输出一致），不得用它决定冲突设备的方向」。其作用是把「距离最小组」排序稳定化；该组内的方向是否一致由 `:329` `distinct` 判定，与顺序无关。
- 冲突处理 `:332-349`：组内非空方向多于一种 ⇒ **不产出任何方向**，记入 `conflicts` 并 `return`。**没有取第一个、没有取人数最多的、没有取字典序最小的。**

⇒ **符合约束**：冲突不会通过人数或字典序等规则被压成一个"看似有效"的方向。

### 3.3 ⚠️ 冲突的可观测性：**不足**（已证实）

### 3.4 ⚠️ `conflicts` 参与的**唯一性覆盖**与暗中丢失（已证实，需仿真确认影响面）

`deviceDirection.js:332` 的 `if (distinct.length > 1)` 只在**距离最小组**（`:320-328`，容差 `DIRECTION_TIE_EPS = 1e-6`，`:31`）内比较方向。

⇒ 若两条路线对同一台设备要求相反方向，但**到该设备的折线距离不相等**（哪怕相差 0.001），则**不判冲突**：距离较小者胜出（`:365-372`），另一条被静默丢弃，且**不进入 `conflicts`、不进入任何诊断数组**。

这是设计有意的（模块注释 `:118-121` 说明第一阶段曾因「节点距离」误判大量假冲突，改用「折线距离」后冲突归零），但副作用是：

- **冲突检出范围被压缩到「几何上等距」的极小窗口**（浮点容差 1e-6）；
- 共享走廊这类「真实存在双向人流」的场景，各条路线的折线距离往往是**对称、完全相等**的（同一批 `CORRIDOR_*` 节点，坐标逐字相同 —— `shared/evacuation/floorTopology.js:147-151`）⇒ 此时距离严格相等 ⇒ **会**被判冲突 ⇒ 不产出方向。
- 反之，距离略有差异（例如设备更靠近 A区分支 0.5px）⇒ **不判冲突**，直接按 A 区路线下发。

⇒ **这不是"由非权威规则裁决"**（它用的是几何距离，属显式模型），但它是**一个未经产品确认的隐性仲裁规则**：「谁离得近听谁的」。需要用户裁决（见 §10 Q2）。

## 5. 共享走廊、楼梯、拐角及 `plan.path` 分析

### 5.1 共享走廊：是否逐段计算（**部分是**，已证实）

- **是**：方向取自路线折线的**局部走向**（`deviceDirection.js:110-137` 注释 ①：每条路线对该设备独立计算候选），不再是整层 `plan.exitSide`；
- **关联距离是「设备到该路线折线的最小距离」**（`deviceDirection.js:164-179`），而非"到某个节点的距离"，模块注释 `:116-121` 记载这是一次真实纠正（原判 EL-5F-05 假冲突）；
- **否（未做到的部分）**：最终取值规则是「**谁最近听谁的**」（`:320-328` + `:365-372`），而**没有**"这台设备同时被多条路线服务"的表达。`deviceDirection.js:18-21` 自身明确标注这是边界：
  > 「灯具 ↔ 拓扑节点 / 路径段」的显式归属契约：本模块用最近点距离近似，不是完整的逐段方向模型。

**结合真实拓扑的推论（需运行期确认）**：`shared/evacuation/floorTopology.js:147-151` 的走廊节点
（`CORRIDOR_N` x=140 / `CORRIDOR_CENTER` x=280 / `CORRIDOR_S` x=415 / `CORRIDOR_W` x=72 / `CORRIDOR_E` x=477，y 全为 170）**被所有楼层的路线共用同一组坐标**。因此：
- 走廊中线上的多台 `evacuation_light`（`src/mock/floorPlanData.js:184-192`，y=170，`x ∈ {72,140,205,280,355,415,477}`，`:204` y 偏移 -8 ⇒ **(x, 162)**）到任何一条经过该走廊的路线的**折线距离恒为 8** ⇒ 若两条路线方向相反 ⇒ **严格等距 ⇒ 判 `conflict` ⇒ 不下发方向**；
- 若同向 ⇒ 正常下发。

⇒ **共享走廊的行为是可预期的，但代价是**：一旦走廊真的出现双向疏散流，**整条走廊的灯全部失去方向**（既无 left 也无 right）。这是"保守不输出"，符合项目约束「不得伪造方向」，但是否是产品的期望行为，需要裁决（§10 Q2）。

### 5.2 楼梯：三条语义无法区分（**已证实**）

`:18-19` 边界：「楼梯平台的『下行 / 上行』语义：需要新增方向枚举，本轮不扩展，相关灯具判为未定」。

**具体到本仓库 topology 的推导（代码可证的几何）**：
- 楼梯节点 `STAIR_NW(72,45)` / `STAIR_NE(477,45)` / `STAIR_SW(72,272)` / `STAIR_SE(477,272)`（`floorTopology.js:153-156`），四个 displaying 楼梯的 x 与两个走廊端点 x 严格重合（72 / 477）；
- 楼梯口疏散灯位置：`floorPlanData.js:239-251`，坐标 `(stair.corridorX, stair.y + stair.h/2)` = **恰好落在 `CORRIDOR_x → STAIR_xx` 这条垂直边上**（x 相同）；
- 因此这些灯触发 `deviceDirection.js:241-244`（`corner-vertical-in-edge`，垂距 ≈ 0）或 `:251-254`（`corner-vertical-out-edge`），或走到 `:198-204` 单点/无水平位移判定的 `no-horizontal-movement`；
- ⇒ **楼梯口全部疏散灯裁决为 `undetermined`，不产出方向。**

| 问题 | 结论 |
|---|---|
| ① 能否区分「进入楼梯」 | **不能**。缺转入竖段的方向枚举，一律 `undetermined` |
| ② 能否表达「下行过程」 | **不能**。同上；`deviceDirection.js:18-19` 明确不在本轮范围 |
| ③ 能否给出「楼层出口指引」 | **不能**。1F 出口在走廊两端（`floorPlanData.js:70-73`，x=32 / x=528），该处的走廊段是水平的可正常裁决（`resolved`），但它是「走廊段的方向」而不是「出口标识的语义」，两者没有被关联 |

⇒ **回答 D2**：当前实现**不区分**进入楼梯 / 下行过程 / 楼层出口指引；楼梯相关灯具一律 `undetermined` ⇒ **没有任何方向输出**。系统**忠实表达"未知"**，但**丧失了楼梯疏散引导能力**。属已知的、模块自带边界，不是 bug，但是**产品可接受性待裁决**（§10 Q3）。

### 5.3 拐角 / 转弯 / 近似几何（**已实现保守降级，已证实**）

`deviceDirection.js:226-256` `cornerOrReversalReason()` 覆盖三类不可靠情形，且**都要求「确认设备落在那条边上」（垂距 ≤ `CORNER_ON_EDGE_EPS = 1e-6`）才降级，不做模糊阈值猜测**（`:220-221`、`:38-39` 注释）：

| 情形 | 返回 reason | 位置 |
|---|---|---|
| 两条腿都水平但方向相反（折返点） | `direction-reversal-at-node` | `:235-238` |
| 入边垂直、出边水平，且设备确认落在垂直入边上 | `corner-vertical-in-edge` | `:239-244` |
| 入边水平、出边垂直，且设备确认落在垂直出边（走廊→楼梯引入段）上 | `corner-vertical-out-edge` | `:245-254`（产品决策 Q1 = 规则乙） |
| 最近 node 无前后邻居或 dx 不可算 | 返回 `null` ⇒ `no-horizontal-movement` | `:184-197`、`:213` |

降级后：`deviceDirection.js:202-204` 把 `dx` 归零、`direction` 置 `null`，原始中心差分保留在 `dxCentered` 供审计。
⇒ **不把拐角近似计算当作可靠指引**这条约束是**被代码兑现的**（保守 return `null` 而非猜测）。

**残留的近似风险（需运行期确认，非缺陷断言）**：`deviceDirection.js:181-197` 取 `prev` / `next` 时**没有做楼层过滤**（只要求 `cur` 同层），`prev`/`next` 可能位于相邻楼层。在本仓库拓扑中，跨层的同名楼梯节点坐标完全一致（`floorTopology.js` 各层 `FLOOR_NODES` 共用同一份 key→坐标），`dx` 因此为 0 ⇒ 走向垂直 ⇒ 判 `undetermined`，结果安全。但若未来拓扑变更使跨层同名节点产生 x 偏移，`dx` 会混入虚假水平分量。⇒ **当前安全，属脆弱依赖**，登记 P3。

### 6.3 状态不一致的具体路径（已证实）

**(a) 路线失效不下撤方向（P1）**

- 路线状态由 `reconcileRouteStatuses()`（`fireStore.js:352-…`）/ `applyExitInvalidation()` 改写 `routePlans[].status`；
- 但 `routeDirectionVerdicts` 的写入点只有 4 个 + 清除点 4 个（`fireStore.js:265 / 1590-1591 / 3809 / 4113-4114`），**没有任何一个由路线状态变化触发**；
- ⇒ 出口被上报为不可用 ⇒ 路线变 `BLOCKED` ⇒ **`routeDirectionVerdicts` 里该路线的 `resolved` 条目仍然存在**，且设备 `d.direction` 仍是按那条（现已失效的）路线算出的值；
- ⇒ 界面继续显示「本轮路线已裁决 + 箭头」，而UI 上该路线本身可能已显示为 BLOCKED。
- **触发条件**：`generateEvacuationOptions`（`:1858`）或 `confirmEvacuationPlan`（`:1932`）/ `adjustEvacuationDirection`（`:3098`）完成选址后，再收到出口 `CLOSED/BLOCKED` 运行态上报。

**(b) 重新规划后方向不更新（P1）**

- `replanRoutesForFire()` / `applyFireBlocking()` / `reconcileRouteStatuses()` **都不调用** `applyBuildingRoutesToDevices`；
- ⇒ 火灾封堵导致改走另一楼梯后，疏散灯方向停留在重规划之前的取值，且裁决状态仍是上一轮的 `resolved`。
- 反向则由 `fireStore.js:1760-1774` / `:2454-2463` 的启发式翻转做局部修补（只处理「正好指向火源」的一批灯，判据是 `d.x` 与 `fireDoorX` 的比较 + 110px 近邻），**不是按新路线几何重算**。

**(c) demo 后端方向 vs 前端裁决（已证实）**

`fireStore.js:576-592`：demo 模式下 `assignDeviceRuntime(d, r)` + `applyStrictDeviceRuntime(d, r)` 会用 WS 快照覆盖 `d.direction`（含 §2.6 的伪随机翻转结果），而 `routeDirectionVerdicts` 保持空 ⇒ 已改造 UI 不显示、未改造 UI 显示翻转后的值。

**(d) `switchEvacuationDirection` 无 demo 守卫导致的短时不一致** —— 见 §4.8。

**(e) `clearRouteFire` / `clearEvacuationRuntime` 与方向的一致性 —— 已正确处理**

- `resetEvacLightDirections()`（`fireStore.js:1585-1591`）在复位前先清 `routeDirectionVerdicts` + `routeNoPathRouteIds`，再按位置重置方向；
- `clearEvacuationRuntime()`（`:252-265`）、`fireStore.js:3809`（方案清空分支）、`:4113-4114`（楼栋级无可用路线）同样成对清理；
- ⇒ **这三条路径状态一致，无残留。**

### 6.4 汇总：是否具备可靠的确认 / 撤销机制

| 机制 | 是否存在 | 结论 |
|---|---|---|
| 方向变更的设备回执 | ❌ | **无法确认** |
| 下发失败检测 | ❌ | **不存在**（无下发） |
| 离线设备的方向过期标记 | ❌ | **不存在**（见 6.2 第三行） |
| 路线失效触发的方向撤销 | ❌ | **不存在**（见 6.3a） |
| 冲突/未定的自动升级 / 告警 | ❌ | **不存在**（见 3.3） |
| 复位 / 清空路径的成对清理 | ✅ | 存在且正确（见 6.3e） |

⇒ **明确结论：当前系统不具备可靠的设备确认或撤销机制。** 它具备的是一套**前端自洽的、可区分 "未知" 与 "有效" 的状态词汇**，且该词汇只在两个 UI 上被兑现。在没有真实下发通道的前提下，这套词汇能诚实表达「未裁决」，但**不能**表达「已下发」「已执行」「已确认」「已过期」。

## 8. 已证实 / 潜在风险 / 证据不足 的明确区分

### 8.1 已证实（有完整代码路径 + 行号，结论不依赖运行数据）
