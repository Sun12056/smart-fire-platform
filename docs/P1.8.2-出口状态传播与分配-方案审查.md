## 3. 建议的阶段目标与明确不做的事项

### 3.1 回答"是否应先统一传播，再做 Zone→Exit 分配"

**建议：是。先做传播统一（Stage 1），再做分配算法（Stage 2）。**

理由：

1. **分配算法的输入依赖正确的候选集**。若传播未统一，`zoneExitReachability` / `planZoneRoutes` 的候选出口里可能包含已 `CLOSED` 的出口 → 分配算法会把人员"分配"到不可用的出口上，产出**看似合理但不可执行**的方案。这是分配层无法自纠的错误。
2. **Stage 1 是纯管道收口，改动面小、风险可控**，且能立即消除 U1/U2/U3。
3. **Stage 1 不触碰 Dijkstra / Yen / 评分 / 几何**，符合既有边界纪律。
4. 顺序颠倒会导致 Stage 2 的成果建立在错误候选集上，返工成本高。

### 3.2 建议的目标（分两阶段，本轮只批准 Stage 1）

**Stage 1 —— 运行态出口状态单一来源与统一传播（建议范围）**

- S1-1：引入出口状态的**单一来源**（初始可为：`EXIT_DEFS` 静态 + 可选运行态覆盖），向四条路径统一提供 `exits`。
- S1-2：为路径 B 的 `planEvacuationRoutes` 增加 `exits` 透传。
- S1-3：路径 C/D 改为经同一过滤（`exitIdsOf` → `availableExitNodeIds(exits)`），不再直连无状态 id。
- S1-4：路径 D 补齐 `validateRoute` 校验，与 C 对齐。
- S1-5：`validateRoute` 若需出口校验，同步补 `buildPlan` 的 `exits` 透传（视 D-5 决策）。

**Stage 2 —— Zone → Exit 分配算法（本轮不做，待 Stage 1 验收后再议）**

### 3.3 明确不做的事项

| 不做 | 原因 |
| --- | --- |
| ❌ 不实现容量（capacity）模型 | 单位/口径/超载策略均未定义，自行设计违反约束 |
| ❌ 不实现拥堵 / 转弯 / 周转评分 | 属 Stage 2 及 P1.8.3 范围 |
| ❌ 不接入真实外部出口状态源（门禁/烟感/外部告警） | 需先明确数据源与协议，且 Stage 1 应以可控方式验证管道 |
| ❌ 不修改 Dijkstra / Yen / `pathCost` / 评分公式 / 几何与墙体 | P1.8.1 边界延续 |
| ❌ 不修改 P1.7 状态机、接口契约、既有 e2e 断言 | 不得修改测试规避失败 |
| ❌ 不删除 `legacyPlans`（除非 D-2 明确批准） | 影响 REST 兼容与 b401 e2e |
| ❌ 不改动 `STAIR_ACTIVE_FLOORS` 及其两个消费者 | 已收敛，无问题 |
