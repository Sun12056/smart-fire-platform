# P1.7 第二阶段 · B-02 审计报告：RESET 后 3D fire / route 残留

> Baseline：`f6b11d5`（B-01 已提交）
> 结论：**RESET 后 3D 不存在「活场景真残留」**。E2E 原先读到的 `fire/route visible=true`
> 是读取了**已卸载场景的陈旧 `__dtwin` 调试句柄**造成的误判，与 B3-04 记录的 **P2-02 同一根因**。
> 本批只修测量口径；P2-02 的产品侧清理因会破坏既有 `browser` 用例而挂账（见第五节）。

---

## 一、审计：fire / route 可见性的权威来源

| 层 | 位置 | visible 由谁决定 |
| --- | --- | --- |
| `FireZone3D` | `src/components/building3d/FireZone3D.js` | 构造即 `visible=false`（:22）；`update(store)` 由 `store.fireEvent` 与当前楼栋 canonical 匹配决定（:86-106），`fireEvent===null` → `visible=false` |
| `RouteLayer3D` | `src/components/building3d/RouteLayer3D.js` | 构造**未设** visible（:19-21，Group 默认 true）；`update(store)` 取 `store.activeBuildingPlan`（主）/ legacy `routePlans`；无方案时 `:57-66` 置 `visible=false`（P2-01：不 dispose tube） |
| 组件 watch | `src/components/BuildingDigitalTwin.vue:166-200` | 订阅 `fireEvent`(:170)、`routePlans`(:179)、`activeBuildingPlanId/activeBuildingPlan`(:183)、`activeRoutePlanId`(:189)、`emergencyStage`(:196) —— **五个源任一变化都会重算两层** |
| 调试句柄 | `BuildingDigitalTwin.vue:121-124` | `window.__dtwin = { scene, model, camera, persons, route, fire, em, rescue, store }`，仅 DEV |

RESET 后 fireStore 侧：`fireStore.js:408-414` 把 `fireEvent=null`、`emergencyStage=0`；
`:266-267 → clearEvacuationRuntime()`（`:235-256`）把 `routePlans / activeBuildingPlanId / activeRoutePlanId` 全部归零。
**只要 3D 组件处于挂载态**，上述 watch 必然触发，两层都会收敛到 `visible=false`。

### 陈旧句柄的成因（P2-02）

```js
// BuildingDigitalTwin.vue:218-225
onBeforeUnmount(() => {
  ...
  if (scene) scene.dispose()   // ThreeScene.dispose() 只释放 RAF/RO/controls/renderer
})                              // ← 没有清理 window.__dtwin
```

`ThreeScene.js:112-120` 的 `dispose()` **不触碰任何 group**，于是卸载后 `fire.group / route.group`
这两个 JS 对象仍然存活，`visible` 冻结在卸载前的最后一值。此后读 `__dtwin.fire.group.visible`
得到的不是「当前画面」，而是**上一轮场景的遗物**。

## 二、实测判定（只读探针 → 固化为专项）

专项：`worker/e2e-p17-batchB02-3d-reset.cjs`
日志：`docs/P1.7-B02-after.log`

| 时刻 | 句柄状态 | 后端 | `fire.visible` | `route.visible` | `route.children` |
| --- | --- | --- | --- | --- | --- |
| 基线 SMART_EVACUATION | 活场景 | SMART_EVACUATION | **true** | **true** | 24 |
| **RESET 后（未离开页）** | **活场景** | IDLE | **false** | **false** | 24 |
| 离开页面（hash → /person） | **陈旧（已卸载）** | IDLE | false | false | 24 |
| **重新进入 3D** | 活场景 | IDLE | **false** | **false** | **0** |

判定：

- **活场景在 RESET 后已正确收敛**（fire / route 均 false）—— 故障不在 fireStore→3D 的权威链。
- **重新进入 3D 后 fire=false / route=false，且新场景 `route.children=0`**（未带入旧几何）—— 满足验收要求。
- journey 原先报的 `true/true` 只可能来自**句柄陈旧时的读取**。

## 三、最小修复（最终落地：只改测量口径）

`worker/e2e-phase3-journey.cjs`：读 3D 状态前先判定句柄是否仍指向挂载中的场景。

```diff
  twin: (() => {
    const w = window.__dtwin
-   if (!w || !w.scene || !w.scene.renderer) return { mounted: false }
+   if (!w || !w.scene || !w.scene.renderer) return { mounted: false, handle: false }
+   // P1.7 批次 B-02：句柄必须指向「当前挂载着」的场景才能读 visible。
+   // 组件卸载后 __dtwin 若未清理，其 group.visible 是冻结的旧值，直接读会误判为 3D 残留。
+   // 未挂载 = 屏幕上没有 3D = 无可见残留，一律记 false。
+   const mounted = Boolean(w.scene.renderer.domElement.isConnected)
+   const vis = (layer, extra) => (layer && mounted
+     ? { visible: Boolean(layer.group.visible), ...extra }
+     : { visible: false, ...extra })
    return {
-     mounted: Boolean(w.scene.renderer.domElement.isConnected),
+     mounted, handle: true, staleHandle: !mounted,
-     route: w.route ? { visible: Boolean(w.route.group.visible), ... } : null,
-     fire:  w.fire  ? { visible: Boolean(w.fire.group.visible), ... } : null,
+     route: w.route ? vis(w.route, {...}) : null,
+     fire:  w.fire  ? vis(w.fire,  {...}) : null,
```

RESET 核对行同步改为「3D 未挂载 = 无可见残留」（挂载时的实质检查在第 25 步重新挂载后进行）。

## 四、尝试过的产品侧修复与回退理由（重要）

按 P2-02 的建议先实现了产品侧清理：

```js
function clearTwinHandle() { if (import.meta.env.DEV) { try { delete window.__dtwin } catch { window.__dtwin = undefined } } }
// onMounted 入口 + onMounted catch + onBeforeUnmount 各调一次
```

专项因此从 22/2 变为 24/0（陈旧句柄项通过）。**但 `test:e2e:browser` 由 96/0 退化为 94/2**：

```
✗ 滞留人员存在且被标记 → 0
✗ 滞留人员未继续沿疏散路线前进（位置冻结） → {"drift":[],"distToExit":[]}
```

原因（`worker/e2e-phase2-browser.cjs:727-738`）：

```js
const strandedSnap = async () => page.evaluate(() => {
  const ds = (window.__dtwin && window.__dtwin.persons.data || []).filter(Boolean)   // ← 依赖句柄
  ...
})
```

该用例在 3D **重挂载 / GLB 加载窗口期**直接读 `window.__dtwin.persons.data`。
`__dtwin` 是在 `onMounted` 末尾（GLB 加载完成后，`:135-137`）才赋值的，
清除句柄后这个窗口内读不到任何实例 → 滞留人员快照为空 → 2 条失败。
（同类依赖还有 `src/components/building3d/RescueLayer3D.js:38-43`，它从 `window.__dtwin.route._lastPoints`
反推救援路线，而该读取发生在 `__dtwin` 赋值之前的首次 `update()`。）

按批次 B 的硬约束「**不修改既有 browser / consistency / api 测试来消除失败**」，
**该次产品改动已回退**（`git checkout -- src/components/BuildingDigitalTwin.vue`），
B-02 的最终落地只保留测量口径修正。

## 五、挂账：P2-02 产品侧清理的前置条件

P2-02 确认与当前现象同根因，但直接清理句柄不可行，需连同下面两处一起改，建议单开一批：

1. `worker/e2e-phase2-browser.cjs:728` —— 用例改用「先确认挂载（`renderer.domElement.isConnected`）再取实例」的取数方式，
   不能依赖卸载/重载窗口期的旧句柄。
2. `src/components/building3d/RescueLayer3D.js:38-43` —— 反向救援路线不应从全局调试句柄取点，
   应改为组件内注入 `route` 层实例（顺带消除「跨场景复用 `_lastPoints`」这一隐患）。
3. 届时 `BuildingDigitalTwin.onBeforeUnmount` 再清 `window.__dtwin`，并覆盖 `onMounted` 的 catch 路径。

另：P2-01（`RouteLayer3D.js:57-66` 只置 `visible=false` 不 dispose tube）仍为挂账项，
实测不是可见残留（新场景 `children=0`，旧场景随组件卸载一起丢弃），属资源释放优化，本批未动。
