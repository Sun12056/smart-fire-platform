## 三、F1 写入口约束、校验方式与字段派生策略

### 3.1 约束

公开写入口 `createManualExecutableRoute` / `replaceManualExecutableRoute` 不再接受任意路线对象透传。现在二者都：

1. 只信任受控输入：`route.nodes`（节点 id 序列）+ 可选 `route.id`。
2. 调用 `buildManualExecutableRoute(route.nodes, id)` 对**待写入路线自身的 nodes**（而非当前 UI 选点状态）重新校验。
3. 校验项：起点 `ROOM/DOOR`、逐段真实邻接、跨层下降方向、终点 ∈ `EXIT_NODE_IDS`、`exitId` 恒等于末节点。
4. 重新派生 `points` / `floorsPassed` / `exitId` / `buildingId`，**忽略**调用方传入的 `points`/`floorsPassed`/`exitId`/`buildingId`/`validated`/`reachable`/`status`/`valid` 等派生或运行时字段。
5. `create`：校验通过后按 id 判重，重复返回 `DUPLICATE_ID`；未提供 id 时用 `genManualRouteId` 生成唯一 `RP-MANUAL-…`。
6. `replace`：校验通过后按 id 整体替换，保留原 `id` / `buildingId` / `createdAt`，更新 `updatedAt`；校验失败返回 `false` 且原记录不变。

### 3.2 字段派生策略

- 路线对象由 `buildManualExecutableRoute` 生成，字段集合固定为 `{ id, type, buildingId, startNode, exitId, nodes, points, floorsPassed, createdAt, updatedAt }`，天然不含 `validated`/`reachable`/`status`/`valid`。
- `replace` 额外用 `prev.buildingId` 覆盖派生值，保证跨楼栋编辑不把旧路线误改楼栋归属（对应 F2 的 buildingId 一致性要求）。

## 四、F2 楼栋上下文重置机制及覆盖入口

### 4.1 机制

`routeBuildingId` 是「当前路线规划楼栋」的唯一权威。新增统一 `watch`：

```js
watch(routeBuildingId, (next, prev) => {
  if (next === prev) return
  resetAuthGraphSelection(null)   // 清 authGraphPath / authGraphDraftId / authGraphError
}, { flush: 'sync' })
```

- `flush: 'sync'`：切换楼栋后**立即**清空旧选点态，杜绝「旧路径 + 新楼栋 buildingId」的时间窗。
- 仅实际变化时重置（同值重赋值不重置）。
- 初始化/恢复快照时的赋值不会误清（编辑态本为空，`resetAuthGraphSelection` 幂等）。

### 4.2 覆盖入口

所有会改写 `routeBuildingId` 的路径最终都经过该 ref，因此统一 watch 覆盖：

- `RoutePlanView.vue` 楼栋下拉 → `onBuildingChange`（`:503`）写 `store.routeBuildingId`（本阶段已移除其内冗余的 `cancelAuthGraphSelection`）。
- `generateRoutePlans`（`fireStore.js` 内 `routeBuildingId.value = buildingId`）。
- `activateBuildingPlansFor`（`fireStore.js` 内 `routeBuildingId.value = bid`，覆盖 dashboard 切楼栋）。

无其它绕过 `routeBuildingId` 的楼栋切换入口。
