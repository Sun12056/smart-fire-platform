## 2. 问题根因与修复方案

### 问题 A：无裁决时仍显示旧方向为有效方向

**根因**：`EvacuationView.vue` 的 `routeVerdictIsStale` 只覆盖 `conflict / undetermined / unlinked` 三种状态。当 `getRouteDirectionVerdict()` 返回 `null`（从未裁决 / 复位后 / 设备不在本轮范围内）时，`routeVerdictState` 为 `null` ⇒ `stale = false` ⇒ 大箭头与方向文字继续按设备里的历史 `direction` 渲染为有效指引。

**修复**：把「箭头是否渲染」的判定抽成**纯函数** `resolveDirectionDisplay(verdict, storedDirection)`（`shared/evacuation/deviceDirection.js`），新增状态 `none`（暂无本轮裁决），规则：

| 状态 | `direction` 输出 | `showArrow` | `stale` | `isValidRouteGuidance` |
|---|---|---|---|---|
| `resolved` | 裁决方向 | ✅ | ❌ | ✅ |
| `overridden` | 覆盖方向 | ✅ | ❌ | ❌ |
| `conflict` / `undetermined` / `unlinked` / **`none`** | **null** | **❌** | 有历史值时 ✅ | ❌ |

**不删除任何历史字段** —— 历史值保留在 `storedDirection` 中，只在提示里以「设备仍保留旧方向『X』，该值非本轮有效指引」呈现。

**UI 接线**（全部改为由判定函数驱动，不再直接读 `device.direction`）：
- 大箭头：`:class="{ ..., 'arrow-invalid': !directionDisplay.showArrow }"`
- 方向文字：`const d = directionDisplay.value.direction; return d ? directionMap[d] : '—'`
- 左右方向键 `active`：`directionDisplay.direction === 'left' / 'right'`

**测试限制声明**：本仓库测试架构不挂载 Vue 组件（`EvacuationView` 依赖 Pinia / Element Plus / 路由），因此**没有**浏览器/E2E 渲染验证。采用的「最小可测设计」是：① 直接单测判定函数（纯函数，即箭头显示判定逻辑本身）；② 源码级断言确认 SFC 的箭头/文字/按钮确实由该函数驱动。不得把 Store 单测冒充 UI 测试 —— 此处两者分开并都做了。

### 问题 B：拐角方向误判（EL-5F-03 / EL-5F-05）

**取证**（实测 5F 拓扑：走廊折线 `y=170`，疏散灯全部在 `y=162`，房间中心 `y=150/190`，楼梯 `y=45/272`）：

| 设备 | 关联到的节点 | 实际落在哪条边 | 当前方向依据 | 结论 |
|---|---|---|---|---|
| `EL-5F-03` (140,162) | `CORRIDOR_N`(140,170)，节点距 8 | **垂直入边** `A_CENTER(140,150)→CORRIDOR_N`，垂距 **0** | 中心差分 `dx = 72−140 = −68`，**全部来自水平出边** `CORRIDOR_N→CORRIDOR_W` | **误判 left**：把出边方向赋给了落在垂直入边上的灯具 |
| `EL-5F-05` (205,162) | `CORRIDOR_N`，两条路线节点距**都是 65.49** | 距西向路线折线 65；距东向路线走廊段 **8** | 旧规则按「节点距相等」判为冲突 | **假冲突**：几何归因错误，不是真实冲突 |

**Q1–Q4 结论**：
1. 设备关联到的是**最近的同层节点**，但真正贴近的是某条**边**；
2. 当前方向来自节点处的**中心差分**，即 `next.x − prev.x`；
3. **能**错误产生 left/right —— 拐角处中心差分的全部水平分量来自出边，而设备落在垂直入边上；
4. 区分方法：比较**到路线折线的关联距离**而非「到最近节点的距离」。节点距相等但折线距不等 ⇒ 归因错误，取折线距更小者；折线距也相等且方向相反 ⇒ 真实冲突。

**修复**（`routeDirectionAtDevice`）：
- ① `distance` 改为**点到路线折线的最小距离**（只计两端同层的线段；该层只有一个节点时退回节点距离）；旧的节点距离保留为 `nodeDistance` 供审计；
- ② 新增 `cornerOrReversalReason()`：入边垂直 + 出边水平 **且确认设备落在垂直入边上**（垂距 ≤ `CORNER_ON_EDGE_EPS`）⇒ 返回 `corner-vertical-in-edge`，**不产出方向**；
- ③ 两条腿都水平但**方向相反**（折返点）⇒ `direction-reversal-at-node`，不产出方向；
- ④ 被判为不可靠时 `dx` 归零（原始中心差分保留在 `dxCentered`），**不留下冒充水平走向的 dx**。

**明确没有采用线段投影方案**：上一轮已证明其在真实布点上退化为 9/11 未定，本轮重新验证结论不变（灯具在 `y=162`、走廊在 `y=170`，最近线段大量落在竖向连接段上）。本轮只改**排序键**与**拐角/折返保守判定**，不改方向来源为「最近线段的走向」。

**修复前后对比**（真实路线 A区→西 / B区→东）：

| 设备 | 修复前 | 修复后 |
|---|---|---|
| `EL-5F-03` | 节点距 8 vs 8 ⇒ **冲突**（无方向） | 关联距 **0**（落在垂直入边）⇒ **未定**，原因 `corner-vertical-in-edge` |
| `EL-5F-05` | 节点距 65.49 vs 65.49 ⇒ **冲突**（无方向） | 关联距 西 65 / 东 **8** ⇒ 归属东向路线 ⇒ **right** |
| 该场景冲突数 | 2 | **0**（两个均为归因错误） |

### 问题 C：手动切换后裁决状态不一致

**根因**：`switchEvacuationDirection`、`batchSwitchEvacuationDirection`、以及两处避火自动反向（`fireStore.js` 原 1280 / 1944）都会写 `d.direction` / `d.recommendedDirection`，但 `routeDirectionVerdicts` 里上一轮的 `resolved` 条目**原封不动**，界面因此仍把「路线已裁决」当作当前方向有效的依据。

**修复**：新增内部函数 `markDirectionOverridden(deviceId, direction, source)`，在四个写入点之后把该设备裁决状态改写为 `overridden` 并记录 `overrideSource`（`manual` / `fire-avoidance`）。只改前端裁决状态，**不新增设备协议字段、不下发任何远程命令、不碰 worker**。

UI 上 `overridden` 渲染箭头但标注「本机覆盖（非本轮路线裁决）」＋「管理员手动切换，未下发设备」，与 `resolved` 明确区分；再次执行路线裁决时会被本轮结果覆盖回 `resolved`。

## 6. 修复前后关键逻辑对比

| 位置 | 修复前 | 修复后 |
|---|---|---|
| 候选排序键 | 到最近同层**节点**的距离 | 到路线**折线**的最小距离（节点距离保留为 `nodeDistance` 供审计） |
| 拐角处方向 | 中心差分 `next.x − prev.x`，水平分量全来自出边 ⇒ 设备落在垂直入边却被判 left | 确认落在垂直入边 ⇒ 返回 `null`，原因 `corner-vertical-in-edge` |
| 折返点 | 无判定（两腿反向时中心差分仍可能给出方向） | 返回 `null`，原因 `direction-reversal-at-node` |
| 不可靠时的 `dx` | 保留中心差分值 | 归零；原始值保留在 `dxCentered` |
| UI 箭头 | 无条件按 `device.direction` 渲染 | 由 `directionDisplay.showArrow` 控制，未可靠裁决时置灰且不作为指引 |
| UI 方向文字 | `directionMap[device.direction]` | `directionDisplay.direction`，非有效时显示 `—` |
| 手动/避火覆盖后裁决状态 | 保留旧 `resolved` | 改写为 `overridden` + `overrideSource` |
| `verdict = null` 时 | `stale = false` ⇒ 旧值被当有效 | `state = 'none'` ⇒ `showArrow=false`、`stale=true` |
