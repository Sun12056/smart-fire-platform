## 2. 专题问答（A~I）

**A. DeviceView 的 building/floor 筛选是否仍属业务判定？**
是。`src/views/DeviceView.vue:555-556`，而且下拉选项写死中文名与 `'1F'..'6F'`（`:34/:43`），filter 直接用 `d.building === buildingFilter`、`d.floor === floorFilter`。**属于业务判定，必须 canonical-first**（→ P1-1）。

**B. 3D PersonLayer3D 的 floor/area fallback 是否只服务渲染？**
是。`PersonLayer3D.js:73-79` 的别名分支只在 `p.buildingId` 完全缺失时进入（且 `bid || wantBldId` 时不进入），`floorId/zone` 一律走 `floorIdOf/zoneOf`；`_fallbackPos` 只在几何坐标缺失时兜底，**不改变归属判定**。判定链符合 canonical-first（→ P2-1，保留）。

**C. FireZone3D / EmergencyLight3D 是否仍存在 alias 主导判定？**
否（非主导）。两者结构相同：canonical 成立时只比 canonical（`FireZone3D.js:81-84`、`EmergencyLight3D.js:36-39`）。
但有两个残留瑕疵：
- `EmergencyLight3D` 的回落开关是「**当前没选楼栋**」而不是「**设备没有 canonical**」→ 未选楼栋时别名会对全部设备生效；
- 两者都不处理「canonical 存在但与别名冲突」的情况（今天由派生保证不冲突）。
→ P1-9 / P1-10，均由 `BuildingModel.applyFireHighlight`（P1-8）放大。

**D. fireStore 的 filter / count / risk / rescue / route / device-binding 是否只认 canonical？**
主体是，例外 3 处：
- `generateRoutePlans:2543` 用 `fireEvent.building === buildingName` 决定是否 `replanRoutesForFire` → P1-5
- `applyDemoPlans:2643` fallback 取 `fireEvent.floor` 作为 `perZone` 的楼层键 → P1-6
- `simulatePerson / simulateRisk` 生成的 riskArea 与 person **不含 canonical** → P1-7 / P1-2（同时影响 risk count）
其余已 canonical：`refreshBuildings:1464`、`refreshPersonStats:1487-1490`、`getDevicesFiltered:1393-1409`、`batchSwitchEvacuationDirection:726-735`、`activateEmergencyResponse:977-997`、`riskAreas.push:1000-1008 / 1667-1673`、`applyRouteToDevices:3015-3025`、`planFireStatus:2856-2861`、`rescueTask:2302-2309`。

**E. Demo snapshot → fireStore 是否存在「canonical → alias → 再反向参与判断」？**
**不存在。**
- 后端序列化：`world.fire = {id, buildingId, buildingName, floorId, zone, ...}`（`engine.ts:126-133`），后端内部全部按 `buildingId/floorId/zone` 判定（`engine.ts:114-119`），从不读 `building/floor/area`。
- 前端落地：`fireStore.js:388-403` 先把 `fireBuildingId` 定死，再**由它派生** `building = BUILDING_ID_TO_NAME[fireBuildingId] || ...`。
- 因此别名永远派生自 canonical，**没有被反向读回**的写法。
- 唯一「从别名反查 id」的入口是 `buildingIdFromName` / `fireBuildingId`（`:869-872`），仅 canonical 缺失时兜底，且查不到返回 `''`（B3-02 已去掉静默回退当前楼栋）。

**F. routePlan / evacuation 是否存在 alias 决定 building/floor/zone？**
不存在判定性用法。
- `RoutePlanView`：`fireLoc`（`buildingIdOf/floorIdOf/zoneOf`）驱动 `isRouteFloorOnFire` / `isFireZone`；`:80-84` 只剩展示文案。
- `EvacuationView:521`：`zoneOf(fireEvent) || riskAreas[0]?.zone`。
- `PersonView:498-502`：`inBuilding()` canonical-first。
- 残留仅 `fireStore:2543/2643`（P1-5 / P1-6）与 `plan.buildingName` 作为**展示/兼容键**（P2-6）。

**G. mock 里的旧字段读取属于哪类？**
全部标为 **「数据生成 / 展示聚合」，不是本阶段业务权威问题**（见 P2-8 明细表）：`mock/statistics.js:62`、`mock/buildings.js:16`、`mock/devices.js:187/199-204/235-237`、`mock/person.js:128-131/165-167`、`mock/lighting.js:64`、`mock/evacuation.js:26`、`mock/deviceSeed.js:44-45`。**本阶段不修改。**

**H. LightingView / lighting 数据源**：按 B4 隔离，本次只记录不改（`LightingView.vue:392/400-401/410`，以及 `fireStore.simulatePersonEnter:2131-2133` 这条「灯 × 新人」匹配属 lighting 数据源边界 → 归 B4，见 P1-11 备注）。

**I. operationLogs**：全部命中均为**文案参数**（如 `fireStore:316/333/1299/2317/2336`），无判定，按 B5 隔离。

## 4. P1：alias 参与业务判断，当前不会立即造成错误

统一格式：文件 + 位置 / 当前逻辑 / canonical 应是什么 / 建议改法

### P1-1 · 只有 alias 的人员对象被写入 store（2 处）
- `src/views/PersonView.vue:727-744`（`handleSimulatePerson`）：直接 `store.persons.push({ building, floor, zone, ... })`，**无 buildingId / floorId**
- `src/stores/fireStore.js:1942-1976`（`simulatePerson`）：同上
- 当前逻辑：对象落成后，靠 `buildingIdOf/floorIdOf/zoneOf` 从别名反查补救；`isCanonicalPerson` 判定为不合格 → `countNonCanonicalPersons()` 会被污染
- canonical 应为：`buildingId: BUILDING_NAME_TO_ID[building]`、`floorId: floorIdOf({floorId: floor})`、`zone`
- 建议改法：两处 push 前统一 `normalizePersonRuntime(...)`（或直接改用 `shared/person/personRuntime` 的 normalize），保证 store 中不存在「无 canonical」人员

### P1-2 · 只有 alias 的 riskArea 被写入 store
- `src/stores/fireStore.js:1996-2010`（`simulateRisk`）：`riskArea = { building, floor, zone, level, ... }`，**无 buildingId / floorId**
- 影响下游：`DashboardView:1513-1515` `riskCount`（走 `r.buildingId ? ... : r.building === bname` 的 alias 分支）、`PersonView:590-592`（走 `r.building || r.floor` 的 alias 分支）→ 两条 risk 来源出现**两套口径**
- canonical 应为：`buildingId` / `floorId` / `zone`（与 `:1000-1008`、`:1667-1673` 两处一致）
- 建议改法：`simulateRisk` 内先 `const bid = buildingIdFromName(targetBuilding)`、`const fid = floorIdOf({ floorId: targetFloor })` 写入对象；随后两个下游的 alias 分支即可整体删除

### P1-3 · 楼栋设备数统计用 OR（别名可反向入账）
- `src/views/DashboardView.vue:1924-1928` `buildingDeviceCount(bname)`
- 当前：`d.building === bname || d.buildingId === b.id`
- canonical 应为：`buildingIdOf(d) === String(b.id)`
- 建议改法：`return (store.devices||[]).filter(d => d && String(buildingIdOf(d)) === String(b.id)).length`

### P1-4 · 应急联动预览台数用别名筛选
- `src/views/DashboardView.vue:1952-1959` `emPreviewCount`
- 当前：`d.building === currentBuilding.value.name && emFloors.includes(d.floor)`
- canonical 应为：`buildingIdOf(d) === String(currentBuilding.value.id)` 且 `emFloors` 用 `floorIdOf(d)` 比对
- 建议改法：`const bid = String(currentBuilding.value.id); const wantFloors = emFloors.value.map(f => floorIdOf({floorId:f})); store.devices.filter(d => d && buildingIdOf(d)===bid && wantFloors.includes(floorIdOf(d)) && ...)`

### P1-5 · 生成路线矩阵时用楼栋中文名判定是否 replan
- `src/stores/fireStore.js:2543`：`if (fireEvent.value && fireEvent.value.building === buildingName) replanRoutesForFire()`
- canonical 应为：`buildingIdOf(fireEvent.value) === buildingId`
- 建议改法：`const fe = fireEvent.value; if (fe && fireLocation(fe).buildingId === buildingId) replanRoutesForFire()`

### P1-6 · 单楼层展示的 perZone 楼层键 fallback 用别名
- `src/stores/fireStore.js:2643`：`const floorId = routeFloorId.value || (fireEvent.value && fireEvent.value.floor) || '5F'`
- canonical 应为：`routeFloorId.value || floorIdOf(fireEvent.value) || '5F'`
- 建议改法：替换别名取值（该键进入 `zoneKeyOf(floorId, zone)`，错误键会导致整层路线取不到）

### P1-7 · `simulatePersonEnter` 用 lighting 设备的别名匹配（边界归属 B4）
- `src/stores/fireStore.js:2131-2133`：`lightingDevices.find(d => d.building === newPerson.building && d.floor === newPerson.floor)`
- 说明：左侧是 `lightingDevices`（B4 数据源），本阶段按 H 节隔离，**不在 B3-03 修改**；但右侧新人推荐先 canonical 化（随 P1-1 一并解决），B4 再统一处理灯侧

### P1-8 · 3D 火区高亮仍是纯别名判定
- `src/components/building3d/BuildingModel.js:281-292` `applyFireHighlight(fe)`
- 当前：`parseInt(fe.floor)` + `e.tag.zone === fe.area`
- canonical 应为：`parseInt(floorIdOf(fe))` + `e.tag.zone === zoneOf(fe)`（并按 `e.tag.floorId` 比对，而非 `parseInt` 后的数字）
- 建议改法：`const fnum = floorIdOf(fe); ... if (String(e.tag.floorId) === fnum && (e.tag.zone === zoneOf(fe) || e.tag.kind === 'wall'))`
- 备注：GLB tag 结构本身不动（不碰 GLB 解析机制）

### P1-9 · EmergencyLight3D 的别名兜底开关取的是「未选楼栋」
- `src/components/building3d/EmergencyLight3D.js:36-39`
- 当前：`(bldId && canonical 比对) || (!bldId && d.building === bldName)` —— 未选楼栋时，即使设备有 canonical 也按别名判定
- canonical 应为：兜底条件是「`!d.buildingId`」而不是「`!bldId`」
- 建议改法：`const list = (store.devices||[]).filter(d => d && (buildingIdOf(d) ? String(buildingIdOf(d)) === String(bldId) : buildingNameOf(d) === bldName))`

### P1-10 · FireZone3D 同上（词面一致，风险更低）
- `src/components/building3d/FireZone3D.js:81-84`
- 建议改法：与 P1-9 同构（保留 canonical-first，删除「未选楼栋即可走别名」的条件）

### P1-11 · `deviceInBuilding` 允许别名匹配覆盖 canonical
- `shared/device/deviceRuntime.js:196-203`
- 当前：`bid === want` 否则再 `buildingNameOf(d) === want` —— 当 `want` 是中文名、设备 canonical 与自身别名冲突时会被误判为命中
- canonical 应为：`want` 先归一为 id（`buildingIdOf({ buildingId: want })`），再用 canonical 比对
- 建议改法：
  ```js
  export function deviceInBuilding(d, buildingIdOrName) {
    if (!d || !buildingIdOrName) return false
    const want = buildingIdOf({ buildingId: buildingIdOrName, building: buildingIdOrName }) || String(buildingIdOrName)
    const bid = buildingIdOf(d)
    if (bid) return String(bid) === String(want)
    return Boolean(buildingNameOf(d) && buildingNameOf(d) === String(buildingIdOrName))
  }
  ```
- 备注：该 helper 被 `fireStore.applyRouteToDevices:3021` 使用，改动面需跑 `test:e2e` + `test:e2e:consistency`
