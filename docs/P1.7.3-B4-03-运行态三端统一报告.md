# P1.7.3-B4-03：应急灯运行态（status / direction / emergencyFlash / brightness / currentMode）三端统一

> 范围：只处理五个运行态字段在 2D / 3D / LightingView 之间的统一。
> 目标：消除第二运行态来源，让三个视图消费同一条权威链。
> 不做：不改路线算法 / GLB / mock 数据结构；不改 B4-01 的 3D 方案订阅；不改 B4-02 已完成的数据源统一；不提前处理 P2-01 / P2-02；不改变灯具位置。

## 一、Baseline：权威链审计（先回答四个问题）

### 1. 五个字段分别由谁产生 / 存储 / 修改 / 消费？

| 字段 | 产生 | 存储 | 修改 | 消费（修复前） |
| --- | --- | --- | --- | --- |
| `status` | Backend `engine.ts`（`EMERGENCY_RESPONSE` 置 `emergency`） | `fireStore.devices`（④ `assignDeviceRuntime`） | 后端 WS 快照 | **仅 2D**（`getDeviceColor(status)`，且 `emergency` 落进绿色分支，与 `normal` 同色） |
| `currentMode` | Backend | `fireStore.devices` | 后端 WS 快照 | **LightingView 只读 `lightingStatus.mode`，而 WS 只写 `lightingStatus.currentMode` → demo 下永远是 `energy`**；2D / 3D 完全不消费 |
| `direction` | Backend（应急联动时整层翻转） | `fireStore.devices` | 后端 WS 快照 | **仅 3D**，且只在 `_bindEvac` 绑定瞬间读一次 |
| `brightness` | Backend（应急置 100） | `fireStore.devices` | 后端 WS 快照 | **LightingView 读全局聚合 `snap.lighting.brightness`**；2D / 3D 完全不消费 |
| `emergencyFlash` | Backend | `fireStore.devices` | 后端 WS 快照 | **无人消费**。3D 用全局 `store.emergencyMode` 代替 |

### 2. 2D / 3D / LightingView 读的是同一份运行态？

**不是。** 修复前实际是三条链：

```
Backend/WS → demoStore.devices → fireStore.devices ─┬─→ 2D   （只取 status，且 emergency 被染绿）
                                                     └─→ 3D   （只取 direction(绑定时) + 全局 emergencyMode）
Backend/WS → snap.lighting（整栋楼聚合）→ fireStore.lightingStatus → LightingView（brightness / mode）
```

`snap.lighting` 与 `devices[i]` 是两个不同粒度的数据源：前者是「整栋楼是否应急」的阶段标志，后者是「每台设备的运行态」。LightingView 站在聚合侧，2D/3D 站在设备侧，两端天然不一致。

### 3. 是否存在并行运行态来源 / 反向写入？

存在，共四处：

1. **`store.lightingStatus`** —— 第二运行态来源。demo 下由 `snap.lighting` 聚合写入 `brightness`，`mode` 字段 WS 从不写入（只写 `currentMode`），因此 LightingView 读到的 `mode` 恒定是初始值。
2. **3D `store.emergencyMode`** —— 全局布尔量被当作设备级运行态使用，非火情楼栋灯具被误强闪。
3. **2D `getDeviceColor(status)`** —— 只按 `status` 取色，`emergency` 落到 `normal` 的绿色分支，应急态不可辨识。
4. **LightingView 反向写入** —— `applyDeviceToStatus` / `handleBrightnessChange` / `handleReset` 会写 `store.lightingStatus.*`（demo 下被 `demoGuard` 拦住，但非 demo 下仍是反向写入）。

### 4. 哪一个是唯一运行态权威？

**`fireStore.devices[i]` 的五个 canonical 字段。**
即：`Backend / WS → demoStore.devices → fireStore.devices → deviceRuntimeState(dev)` 是三端唯一入口；`emergencyMode` / `snap.lighting` 只保留为「全局阶段标志」，不再承担设备运行态职责。

## 三、最小修改

### 1. `shared/device/deviceRuntime.js`（+62，纯新增，无破坏性）

新增统一契约——三端唯一读取入口：

- `deviceRuntimeState(d)`：五字段纯值快照（`status / currentMode / direction / brightness / emergencyFlash`）
- `isDeviceEmergency(d)`：`emergencyFlash || currentMode==='emergency' || status==='emergency'`
- `deviceBrightness(d)` / `deviceBrightnessRatio(d)`：`0~100` / `0~1`
- `deviceDirection(d)`：恒 `left | right`
- `deviceIsOnline(d)`、`isLightingDevice(d)`、`isEvacuationLight(d)` 等

### 2. `src/components/building3d/EmergencyLight3D.js`

- `tick()` 不再读全局 `store.emergencyMode`，改为**逐设备**读 `deviceRuntimeState(dev)`；
- 新增 `_syncRuntime()`：把实际消费到的运行态写入 `rec.runtime`（三端一致性自检入口）；
- **新增逐帧按 id 重新解析权威对象**：`fireStore.devices` 可能在运行中被整体换数组（`loadFromRemote` / `resetAll`），旧实现缓存的 `rec.device` 会变成孤儿快照，方向翻转与亮度变化永远到不了 3D；
- `direction` 每帧比对、按需换贴图（不再只在 `_bindEvac` 时读一次）；
- 光强基准随权威 `brightness`（`base = 0.4 + 0.6 * ratio`），离线设备归零；
- **B4-01 的 3D 方案订阅未改动**；疏散箭头仍恒用绿色（`COLORS.arrow`），强闪只作用于暖白照明灯。

### 3. `src/views/BuildingView.vue`（2D）

- 点位新增 `data-id / data-status / data-mode / data-flash / data-brightness / data-dir`（即本次渲染实际使用的运行态）；
- 新增 `devColor / devGlowKey / devGlowOpacity / devFlash / devBrightness / devDir / devDirPath`，全部走统一契约；删除只按 status 取色的 `getDeviceColor`；
- 应急态用暖白 `#F8F3E4` + 新增 `device-glow-emergency` 光晕（与 3D 应急照明灯同色），不再与常态绿色混淆；
- 光晕强度随权威 `brightness`；
- 疏散指示灯新增绿色方向箭头（`fill="#22C55E"`，恒绿，禁止红/橙/蓝替代）；
- `statusLabel` 补齐 `emergency → 应急`；
- **设备位置（`getDeviceX/Y`）完全未改动**。

### 4. `src/views/LightingView.vue`

- `brightness / currentMode / personDetected / ambientLabel` 全部改为读「当前选中的权威设备」，不再读 `lightingStatus`；
- 新增 `deviceFlash`，根节点输出 `data-device-id / data-brightness / data-mode / data-flash`；
- `applyDeviceToStatus` 只同步本地滑块，不再反向写 `lightingStatus`；`handleBrightnessChange` / `handleReset` 同理（非 demo 下本地控制的唯一落点就是权威设备本身）；
- 新增 `watch(brightness)` 同步滑块，保证 WS 下发 / 楼栋楼层切换 / 模式切换都跟随权威。

### 5. `src/stores/fireStore.js`

`⑤ 照明`：`snap.lighting` 只保留 `emergencyMode`（全局阶段标志）；`lightingStatus` 降级为「选中设备的展示镜像」，其 `brightness / currentMode / mode / status / currentDevice` 一律由权威设备派生，不再是第二运行态来源。

## 七、过程中修掉的一个真实缺陷（附带）

修复 B4-02 回归时发现：`LightingView.vue` 若在根 `<div>` **之外**写注释，模板会变成 Fragment 根，破坏 `App.vue` 的 `<transition mode="out-in">`，导致**离开照明页后所有路由渲染空白**（`.content-area` 只剩 `<!---->`）。
已在 `LightingView.vue` 顶部留注释固化此约束，并在 `worker/e2e-p173-b403-runtime-unity.cjs` 中用「二次进入 `#/lighting`」的用例间接覆盖。

## 八、遗留观察（不在本批范围，仅记录）

1. **2D 与 3D 的「当前楼栋」不是同一个 state**：`BuildingView` 持有自己的 `selectedBld`（只在楼栋列表点击时更新），而 3D 各层只认 `dashboardView.selectedBuildingId`。二者未联动，属「选择态」而非「运行态」，不在 B4-03 范围（P2 相关）。本次测试通过点击楼栋列表来对齐两端。

3. **b402 偶发路由时序竞态（独立待办，本轮不改脚本）**：demo+WS 环境下首跑 20/4、复跑 24/0；4 个失败项全为 T2（`.device-selector` / `.device-info` 未在 20s 内出现），直接加载 `#/lighting` 路由时 DOM 正常。根因**目前倾向于 E2E 路由切换时序问题，仍需后续验证**，详见 §六 复验补注 3。
