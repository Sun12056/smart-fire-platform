## 二、指令链审计结论（决定改法）

后端唯一权威迁移表 `worker/src/demo/stages.ts:33-42`：

```
FIRE_DETECTED:    { ACTIVATE_RESPONSE → EMERGENCY_RESPONSE, RESET → IDLE }
RETAINED_PERSONS: { CONFIRM_RETAINED  → RESCUE_COORDINATION, RESET → IDLE }
```

- 不存在 `VIEW_FIRE` / `ACK_FIRE` 中间指令，`FIRE_DETECTED` 的唯一推进指令是 `ACTIVATE_RESPONSE`。
- 现有可复用指令链（fireStore → `dispatchDemoCommand` → demoStore → REST → DemoRoom）：
  - `store.activateEmergencyResponse()` → `ACTIVATE_RESPONSE`（弹窗②已在用，验证有效）
  - `store.confirmStrandedLocation()` → `CONFIRM_RETAINED`（弹窗③已在用，验证有效）
- 断裂根因：`DashboardView` 的 `confirmFireIncident` / `confirmStranded` **完全没走这两条链**，只做前端本地记账 / 开弹窗。

### 指令归属冲突与审批决策

同一条后端迁移只能被消费一次，而 FIRE_DETECTED 上有 3 个入口、RETAINED_PERSONS 上有 2 个入口：

| 阶段 | 入口 | 决策后归属 |
| --- | --- | --- |
| FIRE_DETECTED | 查看火情 / 确认火情 / 启动应急预案 | **确认火情** 拥有；查看火情维持 UI 记账；启动应急预案变幂等确认 |
| RETAINED_PERSONS | 确认人员位置 / 启动应急协同救援 | **确认人员位置** 拥有；弹窗③变幂等确认 |

已审批：确认火情拥有该迁移；验收判定由「必须推进」改为「**后端 stage 必须落到目标阶段**」（本步推进 or 上游已推进均算通过，仍是后端 stage 判定，不看 UI）。

+async function confirmStranded() {
   if (!store.strandedPersons.length) return
   showRescueDialog.value = true

要点：

- **不新建状态机、不改后端契约**，复用 `activateEmergencyResponse` / `confirmStrandedLocation` 两个已有 fireStore 函数，

- **不在前端自行改 stage**，阶段仍由后端 snapshot 回来。
- **弹窗出现 / 关闭行为零改动**：`showFireConfirmDialog=false`、800ms 弹窗②、`showRescueDialog=true` 全部保持原样。
- 幂等安全：重复下发时 `dispatchDemoCommand` 因 `allowedCommands` 不含该指令而静默返回，不产生后端 409 报错（专项 T2.7 / T3.6 已验证 `err=null`）。
