## 1. 结论摘要（先说结果）

1. **R-01 与 R-11 必须同批**，不是流程偏好，而是硬依赖：R-01 单独落地会把 demo 模式的方向显示**从「四视图分裂」直接变成「四视图全无方向」**（因为 demo 模式裁决表恒空，接入严格判定后 `showArrow` 恒为 false）；R-11 单独落地则只改数据、四个视图里仍有两个（2D / 3D）不认裁决表，**看不到任何改善**。二者是「同一根因的两个半区」：**裁决表是唯一显示依据，但表里缺了 demo 的来源，而两个视图根本不读这张表**。
2. **本批引入一个来源维度**：裁决表新增 `remote`（后端运行时下发）状态，用于表达「demo 模式下方向来自后端运行态，不是路线几何裁决」。不这样做，就只能让 demo 方向冒充 `resolved`（**语义撒谎**，违反项目「不得宣称未发生的语义」红线），或让 demo 永无方向（现状缺陷）。
3. **R-08 的结论是收紧，不是放宽**：`overridden` 不再一律渲染箭头 —— 只有 `overrideSource === 'manual'`（管理员显式设定）才渲染；`fire-avoidance`（由旧值翻转而来）不渲染方向，只保留状态与提示。这是把「陈值洗白」的入口直接关掉。
4. **显示面从 4 个变成 5 个**：除 `BuildingView`(2D) 与 `EmergencyLight3D`(3D) 外，`EvacuationView` 的「疏散设备状态」列表仍在直读 `dev.direction`（`:433`），属同一缺陷类的漏点，必须一并收口。
5. **本批不改**：`worker/src/**`、拓扑 / Dijkstra / Yen / `pathCost` / 规划器、`direction` 取值域（仍只有 `left`/`right`）、设备协议字段、故障与离线维度（R-04 排除）、路线失效失效（R-03 排除）、单路线入口收敛（R-02 排除）。
6. **可回滚**：全部改动是 6 个前端文件 + 测试，无持久化、无协议、无数据迁移；部分回滚的最坏结果是「显示不出方向」，不会伪造方向。

**铁律（本批建立，写入代码注释与测试）：**

1. 显示方向**只能**由 `resolveDirectionDisplay()` 得出。除审计 / 日志 / E2E 采集外，**禁止**在视图层直读 `deviceDirection(dev)` 或 `dev.direction` 决定「是否画箭头 / 画哪个朝向」。
2. 裁决表**只允许整表覆盖写**（`xxx.value = 新数组`），禁止 `push` 追加、禁止就地改写元素。此约束是 3D 侧缓存失效键（数组引用）成立的前提（§8.4）。
3. 每个模式**只有一个主写者**（demo：快照投影；mock/api：路线裁决），由**方向相反的守卫**保证互斥（§6.5）。

### 5.2 生成规则（逐台）

| 输入形态 | 输出条目 |
|---|---|
| `d.type ∈ {'evacuation_light','emergency_light'}` 且 `d.direction ∈ {'left','right'}` | `{ deviceId, state: 'remote', direction, source: 'demo-backend' }` |
| 同上但 `direction` 缺失 / `null` / 非 `left|right` | `{ deviceId, state: 'undetermined', source: 'demo-backend', reason: 'backend-direction-missing' }`（**不得**用 `directionOf()` 的 `'right'` 兜底值来造方向） |
| `d.type` 非灯具 | 不产生条目 |
| store 中存在但**不在本次 `snap.devices` 内**的灯具 | 不产生条目 ⇒ 该设备回落 `none`（无箭头）；上一轮残留条目随整表覆盖一并消失 |

**为什么两个灯型都要覆盖**：`shared/device/deviceRuntime.js:144` 的 `LIGHTING_DEVICE_TYPES` 把两类灯都视为灯具，`worker/e2e-p173-b403-runtime-unity.cjs:127` 的 `isLight()` 同样包含两者，且 2D 的 `data-dir` 写在**所有**设备节点上。若只覆盖 `evacuation_light`，`emergency_light` 会在 demo 下变成「无方向」，直接击穿既有 B4-03 三端一致性断言（`:338-352` 的 `missing` 桶）。

### 5.3 与设备字段的关系（本批不改写入行为）

- `applyStrictDeviceRuntime`（`:724-732`）继续把后端 `direction` 整字段写入设备 ⇒ `dev.direction` 仍是权威原值，**不删除、不清空、不改取值域**。
- 新增的是**第二层语义**：「设备字段里是什么」（`dev.direction`）与「本轮能否作为方向指引显示」（裁决表）分离。这与第一阶段 `deviceDirection.js:43-45` 的既有声明一致：「裁决状态是前端/审计词汇，不是设备协议字段」。
- 因此本批**不新增任何设备字段、不改 WS 载荷、不改 D1**。

### 5.4 幂等与防抖

- 投影结果先与当前表做**结构化签名比对**（对 `deviceId/state/direction/source/reason` 排序后序列化）；相同则**不赋值**，避免每个快照都触发一次全站重渲染。
- 写入为整表替换（§4 铁律 2），不做增量 patch。

### 5.5 明确不做的两件事

1. **不修改 `worker/src/demo/engine.ts:149-166` 的伪随机翻转**（R-05），也不修改其事件文案。⇒ 后果：demo 模式下 `remote` 方向在 `EMERGENCY_RESPONSE` 阶段仍是「约 50% 随机翻转」的结果，UI 会如实标注「演示态下发（非路线裁决）」，**不得**把它描述成「按火源反向」。
2. **不引入「快照年龄 / 断线过期」维度**（属 R-04 同域）：WS 断开期间裁决表保持最后一次快照结果，界面不额外标注过期。此边界必须在实施报告中复述，避免被误认为已修 R-04。

### 5.6 与 R-09 的交互（已知、不修、需固化）

`switchEvacuationDirection`（`:2978-2988`）**没有 `demoGuard`**（R-09）。本批之后的行为变为：

```
手动切换 → markDirectionOverridden(manual) → 界面短暂显示「本机覆盖(manual)」
```

⇒ **demo 模式下「本机覆盖」的生命周期 ≤ 一个快照周期**。这与「后端是唯一权威」一致，**不属于本批缺陷**，但必须在契约与测试中显式固化，禁止在实施报告里写成「已修复 R-09」。

### 6.2 唯一判定函数（行为表）

`resolveDirectionDisplay(verdict, storedDirection)` 输出语义（**入参签名不变**）：

## 7. 覆盖状态处理规则

### 7.1 `overridden` 的三问（R-08 设计审查结论）

| 问题 | 现状（`deviceDirection.js:396-416`） | 本批结论 |
|---|---|---|
| 谁写？ | `fireStore.js:1517`（批量手动）、`:2987`（单设备手动）、`:1772` / `:2462`（避火自动反向），经 `markDirectionOverridden`（`:4230-4241`） | 写点**全部保留**，不改写入时机 |
| 依据是否可信？ | `manual` 是显式人工定值（可信）；`fire-avoidance` 是 `flip(旧方向)`，输入可能是从未裁决过的种子值（**不可信**，见《审计》§4.7） | 由 `overrideSource` 区分，无需新增 basis 字段 |
| 能否显示？ | 一律 `showArrow = true`（`:401,411`） | **`manual` 显示；其余来源不显示**（fail-closed，未知来源默认不显示） |

配套：`DIRECTION_OVERRIDE_SOURCE_LABELS`（`:71-74`）保持不变；新增导出 `OVERRIDE_DISPLAYABLE_SOURCES = ['manual']`，供 UI 文案与测试引用，避免规则散落。
### 7.2 写者 / 覆盖矩阵

| 写者 | 生效模式 | 写入方式 | 覆盖范围 | 触发时机 |
|---|---|---|---|---|
| `applyRoutesToDevices`（`:4198`） | mock / api | 整表替换 | 本轮全部目标设备 | 路线裁决 |
| `applyBuildingRoutesToDevices` 全阻分支（`:4112-4114`） | mock / api | 整表清空 | 全部 | 无任何可执行路线 |
| `projectDemoDirectionVerdicts`（新增） | **demo** | 整表替换 | 快照内全部灯具 | 每次 full snapshot |
| `markDirectionOverridden`（`:4230-4241`） | 两模式 | **单条不可变替换** | 单设备 | 手动 / 避火 |
| 清空点（`:264`、`:1590`、`:3808`） | 两模式 | 整表清空 | 全部 | 复位 / 方案清空 / 清火 |

### 7.3 失效与清除规则

| 事件 | 裁决表动作 | 依据 |
|---|---|---|
| 新一轮路线裁决 | 整表替换（旧条目全部消失） | `:4198` 既有行为 |
| 新一次快照 | 整表替换（含「设备已不在快照内 ⇒ 条目消失」） | 本批新增 |
| 设备被手动切换 | 该设备单条 → `overridden` | `:4230-4241` |
| 复位 / 清空方案 / 清火 | 整表清空 | `:264`、`:1590`、`:3808` |
| 路线失效 / 设备离线 / 快照断线 | **不做任何动作** | R-03 / R-04 排除，见 §2.3 |

### 7.4 不可变写入（本批唯一的「写侧」风格变更）

`markDirectionOverridden` 目前就地改 `list[idx] = entry` / `list.push(entry)`。本批改为：

```
新数组 = 旧数组.filter(≠deviceId).concat(entry)
routeDirectionVerdicts.value = 新数组
```

理由（三点，均为可验证的工程约束）：

1. 3D 侧以数组引用作为缓存失效键（§6.4），就地改会导致箭头**不刷新**；
2. 与主写者的「整表替换」风格统一，避免出现「数组引用不变但内容变了」的观察者漏检；
3. 现有消费方全部经 `getRouteDirectionVerdict` / `directionVerdictIndex`，不受实现方式影响。

### 7.5 明确不在本批引入的覆盖维度

`expiresAt` / `staleReason` / `deviceOnline` / `routeInvalidated` —— 四个字段**一律不新增**。理由：它们分别属于 R-03 / R-04，混入会同时改变「谁能显示方向」的判定维度，使本批的验收矩阵（6 态 × 5 显示面）失去封闭性。
