## 三、N-5 实际触发路径（3 条，均为代码路径确定）

### P1（最严重）· demo 切换楼栋后裁决表长期为空

```
用户切换查看楼栋
  → watch(dashboardView.selectedBuildingId)            fireStore.js:3872-3875
  → activateBuildingPlansFor(bid)                      :3839
  → demo 分支：routeDirectionVerdicts.value = []       :3858   ← 表被清空，签名不动
  → 下一次 full snapshot（设备方向与上次投影相同）
  → applyDemoSnapshot :573 → ④ 设备合并 :577-597
  → projectDemoDirectionVerdicts(list)                 :767
  → signature === demoVerdictSignature（旧值）→ return :774   ← 不再写入
  ⇒ 表持续为空，直到某台灯的 DTO 方向发生变化
```

**后果**：demo 演示中「切一次楼栋再切回来」即可能让该楼栋全部疏散灯**永久失去方向**（裁决表空 ⇒ 所有显示面都拿不到 `remote`）。这是 N-5 最严重、也最容易在演示现场复现的形态。

### P2 · demo RESET/IDLE 快照：「先清空、后跳过」

```
snapshot(stage=IDLE, buildingPlans: [])
  → applyDemoSnapshot :505
  → ②·补充 applyDemoPlans(snap)                        :573
  → buildingPlans 为空数组 → clearEvacuationRuntime()  :404 → :264（清空表，签名不动）
  → ④ 设备投影 :597 → 签名相同 → 跳过（:774）
  ⇒ 表为空
```

**后果**：同一 IDLE 快照若重复到达，会表现为「**第一次有箭头、之后无箭头**」的抖动（首次投影签名不同 → 写入；随后被清空 + 跳过）。是否显现取决于后端是否在 IDLE 快照中携带 `buildingPlans: []`（`applyDemoPlans` 的注释表明这是预期载荷）。

### P3 · 覆盖写后相同快照无法收敛回 `remote`（S2 测试未覆盖）

```
① 快照 A 投影 → 表 = A(remote)，签名 = S_A
② 手动切换 → markDirectionOverridden :4289 → 表 = A 但该设备变 overridden（签名仍 S_A）
③ 再次收到**完全相同的快照 A** → 签名 S_A === S_A → 跳过
⇒ 该设备永远停留在 overridden，违反 v2.1 §5.6「下一次快照覆盖回 remote」
```

**为什么 S2 的 S7 没抓到**：S7 用的第二次快照内容与上一次投影**不同**（`[lights[0]]` → `[lights[0], lights[1]]`），签名自然变化，属"侥幸通过"。**这是 S2 测试设计的一个覆盖缺口。**

## 五、最小修复方案

### 5.1 方案 A（推荐）：幂等基准取自当前表，取消影子状态

**核心思路**：判断「是否与表的当前内容相同」而不是「是否与我上次写过的东西相同」。表被任何写者清空或改写后，内容签名自然不再相等 ⇒ 必然重新写入；表未被改动时签名相等 ⇒ 保持引用不变。

```js
  /** 裁决表内容签名：demo 投影的幂等基准（取自当前表，不设影子状态） */
  function directionVerdictSignature(list) {
    return (Array.isArray(list) ? list : [])
      .map((v) => `${v.deviceId}|${v.state}|${v.direction || ''}|${v.reason || ''}`)
      .sort()
      .join('\n')
  }

  function projectDemoDirectionVerdicts(entries) {
    if (!dataSource.isDemo) return
    const list = Array.isArray(entries) ? entries : []
    // 幂等基准取自当前表：表被清空或改写后，相同快照必须重新写入
    if (directionVerdictSignature(list) === directionVerdictSignature(routeDirectionVerdicts.value)) return
    routeDirectionVerdicts.value = list
  }
```

**改动规模**：`src/stores/fireStore.js` **+6 / −3**（删除 `:766` 1 行、抽出签名函数 5 行、比较行 1 行改写、1 行注释）；无其他文件源码改动。

### 5.2 逐条满足性核对（对照评审提出的 5 项约束）

| # | 约束 | 本方案为何满足 |
|---|---|---|
| 1 | 快照 A 投影成功后表包含 A | 首次签名不等（表为空或旧内容）⇒ 写入 |
| 2 | 表被清空后，再次收到相同 A 必须重建 | 清空后当前表签名为 `''`，与 `sign(A)` 不等 ⇒ 写入（**与清空由谁触发无关**） |
| 3 | 无清空、内容未变时重复快照，数组引用不变 | 两侧签名相等 ⇒ 提前 return，不触碰 `.value` |
| 4 | 不改变 Demo / 非 Demo 双写者互斥 | `if (!dataSource.isDemo) return` 原样保留；调用点 `:597` 的 `authoritative` 判断不变 |
| 5 | 不改变白名单、`remote` 状态与既有裁决语义 | 只替换「是否写入」的判据，不触碰 `demoDirectionVerdictOf`、`resolveDirectionDisplay`、任何 state |
| 6 | 不扩大范围 | 不触 `deviceRuntime.js`、视图、`worker/src/**` |
| 7 | 不引入不必要注释 / 重构 | 仅 1 行必要注释；签名抽函数是为复用（两处调用），非重构 |

### 5.3 否决的替代方案

| 方案 | 做法 | 否决理由 |
|---|---|---|
| **B** | 保留影子变量，在 W1–W4 四处清空后各加 `demoVerdictSignature = ''` | ① 需改 5 处（含 `clearEvacuationRuntime` 内部与 `activateBuildingPlansFor`），侵入性更大；② **未来任何新增清空点都会重新引入该缺陷**（无强制约束）；③ **无法修复 P3**（覆盖写仍不推进签名） |
| **C** | 比较 `长度` 或 `JSON.stringify(list)` 与表 | 长度比较会漏「同长度不同内容」；`JSON.stringify` 对字段顺序敏感且包含 `candidates` 大对象，跨轮次不稳定（同一语义不同构造顺序会误判为变化） |

### 5.4 修复带来的一个行为变化（需评审确认）

修复后，**IDLE 快照也会稳定保留 `remote` 条目**（不再出现「先清空、再跳过」导致的空表）。理由：投影契约本就是「每次快照按设备方向重述一遍」，与 2D/3D 现有展示（一直显示方向）一致；稳定性优先于「IDLE 时不显示方向」的隐含假设。
⇒ **若产品要求 IDLE 不显示方向**，应通过「状态语义」（例如 IDLE 不下发 `remote`）在**投影函数内显式表达**，而不是依赖签名跳过这一副作用 —— 这属于**独立需求**，本方案不擅自引入。

### 5.5 已知次要限制（不改）

签名不含 `overrideSource` / `source` / `routeId` / `distance`。投影列表字段同构（恒为 `remote|undetermined` + `source:'demo-backend'`，无 `routeId`/`distance`），因此不构成实际风险；且表内一旦出现 `overridden`，`state` 已能区分。**记录不改，避免扩大比较语义。**
