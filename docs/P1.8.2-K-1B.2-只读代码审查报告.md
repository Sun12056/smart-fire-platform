## 三、按 A–E 逐项审查结论

### A. 权威图与楼栋上下文

**结论：已满足（含 1 项非阻断风险，见 F2）。**

- `authoritativeRouteGraph`（`fireStore.js:1031`）= `buildBuildingGraph(getBuildingFloors(currentManualBuilding().id))`，由 `currentManualBuilding()`（`:1021`）以 `routeBuildingId` 可靠解析当前楼栋；不匹配/空 id 返回 `null`，层数 `Number.isFinite && > 0` 校验，建图异常 try/catch 返回 `null`。**明确失败，无默认回退**。
- UI 选点与校验共享同一 computed，`RoutePlanView.vue` 未重复推导层数/建图（`:607` `authGraph = store.authoritativeRouteGraph`）。
- 楼栋切换：UI `onBuildingChange`（`RoutePlanView.vue:503–509`）会 `store.routeBuildingId = ...` + `store.cancelAuthGraphSelection()`，常规手动模式切楼栋会清除编辑态。
- **风险 F2**：store 层其它改 `routeBuildingId` 的路径（`generateRoutePlans:2840`、`activateBuildingPlansFor:3256/3270/3277`）不重置 `authGraphPath`/`authGraphDraftId`，可能残留旧楼栋选点路径（详见 F2）。

### B. 路线选点与跨层约束

**结论：已满足（含 1 项非阻断风险，见 F1）。**

- 起点：`isAuthStartNode`（`:1055`）仅 `NODE_TYPE.ROOM || NODE_TYPE.DOOR`。
- 邻接：`appendAuthGraphNode`（`:1196`）经 `canAuthStep`（`:1077`）先校验 `g.adj[fromId]` 真实含 `toId`，再校验跨层下降方向 `floorNum(from) > floorNum(to)`。
- 下降边合法性：图中唯一跨层边即 `STAIR_DESCENT`（由 `stairDescentEdgeDefs` 按 `isStairActiveOnFloor` 门控生成），因此「真实邻接 + 下降方向」联合即证明是合法下降楼梯边；楼层数字比较**不单独**作为合法性证据（审查任务书特别提示点，已核对）。
- 楼梯停用/缺失邻接/无效节点：`canAuthStep` 返回 false；`buildManualExecutableRoute`（`:1098`）对 `UNKNOWN_NODE`/`NOT_ADJACENT`/`INVALID_START_TYPE`/`INVALID_EXIT` 逐项拒绝。
- 终点：`isAuthExitNode`（`:1090`）仅 `EXIT_NODE_IDS.includes`；`exitId = ids[ids.length-1]`（`:1113–1134`），恒等于终点节点。
- **风险 F1**：`createManualExecutableRoute`（`:1251`）/`replaceManualExecutableRoute`（`:1260`）是**公开且不校验**的写入口，可绕过上述所有约束直接写入任意 `nodes` 序列（详见 F1）。UI 仅走 `saveAuthGraphRoute`（`:1233`，经 `buildManualExecutableRoute` 校验），故生产 UI 路径当前安全。

### C. 独立路线生命周期与隔离

**结论：基本满足（含 F1 关联项）。**

- `manualExecutableRoutes`（`:1011`）为独立 ref，未并入 `routePlans` / `routeMatrix.perZone` / `activeBuildingPlan.routes`。
- 创建防重复 ID（`:1254`），替换按 ID 不累积（`:1260`），删除按 ID（`:1273`）。
- 自由绘制仅写 `manualRouteDrafts`（`saveManualRoute:3999`），不再写 `routePlans`；`deleteManualRouteDraft`（`:4019`）。
- UI 无绕过：仅调用 `saveAuthGraphRoute` / `loadAuthGraphRouteForEdit` / `deleteManualExecutableRoute`（`RoutePlanView.vue:324/698/706`）。
- **F1 关联**：`createManualExecutableRoute`/`replaceManualExecutableRoute` 是唯一能绕过规范图约束写入手动可执行路线的入口（已导出，`:4323–4324`）。全仓搜索确认除这两者 + 恢复清洗 + 测试外无其它 `manualExecutableRoutes` 写点。

### D. 持久化与恢复

**结论：已满足（含 F1 关联的字段剥离小项）。**

- `manualExecutableRoutes` 入 `persistRefs`（`:4056–4057`），与既有机制一致；`watch(deep)` 自动纳入。
- 旧快照缺字段：`restorePersistSnapshot` 仅写 `snapshot[k] !== undefined` 的键，恢复后清洗块（`:4092–4101`）对空集合处理，安全。
- 结构损坏 vs 拓扑失效：`sanitizeManualExecutableRoutes`（`:1150`）只做结构校验（对象 / id 字符串 / nodes 字符串数组 / exitId 字符串），**不**做拓扑校验；结构损坏剔除并记 `manualRoutesRestoreReport`，结构完整但拓扑失效**保留**。
- 恢复后不把「记录存在」当「有效」：`sanitize` 不写 `valid`/`validated`/`status`，路线不带运行时结论（`buildManualExecutableRoute` 产出的对象无这些字段）。
- **F1 关联小项**：`createManualExecutableRoute`/`replaceManualExecutableRoute` 用 `{...route}` 透传，若调用方传入 `validated`/`reachable`/`status` 等字段不会被剥离，可能被持久化（正常 `saveAuthGraphRoute` 路径不会产生）。

### E. 与后续准入阶段的接口

**结论：已满足。**

- 数据源提供原始待校验数据（id / buildingId / startNode / exitId / nodes / points / floorsPassed / 时间戳），K-1B.3 可读。
- 无「可保存 = 已通过安全校验」逻辑：路线不携带 `validated`/`valid`/`status`；`type: 'manual-executable'` 仅为数据源命名，语义上未被任何疏散决策消费。
- 无路线参与真实疏散决策：`manualExecutableRoutes` 未被 `reconcileRouteStatuses` / `applyExitInvalidation` / `applyBuildingRoutesToDevices` / 设备执行入口消费（专项测试第十二节断言隔离）。
- 未接入设备执行、出口运行时协调、自动路线状态逻辑。

## 四、问题清单（等级 + 证据）

### F1【非阻断风险 · 建议 K-1B.3 前整改】未校验的公开写入口

- 位置：`src/stores/fireStore.js:1251–1258`（`createManualExecutableRoute`）、`:1260–1271`（`replaceManualExecutableRoute`）；导出于 `:4323–4324`。
- 证据：`createManualExecutableRoute` 仅做 `route` 为对象 + 重复 id 判断，随后 `manualExecutableRoutes.value.push({ ...route, id: routeId })`；不校验起点类型、邻接、下降方向、`exitId ∈ EXIT_NODE_IDS`、`exitId === nodes` 末位、`nodes` 类型，也不重新派生 `points`/`floorsPassed`（直接信任调用方传入值）。`replaceManualExecutableRoute` 同理按 id 整体替换不校验。
- 影响：任何调用方（未来代码/测试）可绕过权威图约束写入任意 `nodes`，或写入 `exitId` 与末位不一致、或携带 `validated:true` 等字段的路线。
- 当前缓解：UI 仅走 `saveAuthGraphRoute`（`:1233`，经 `buildManualExecutableRoute` 校验），故现有生产 UI 路径安全；且这些路线尚未参与任何疏散决策。
- 建议：① 让 create/replace 复用 `buildManualExecutableRoute` 校验，或 ② 不导出/降级为内部函数，或 ③ 明确文档化「唯一合法写入口 = `saveAuthGraphRoute`」并由测试锁定 create/replace 拒绝非法输入。

### F2【非阻断风险】楼栋切换（store 层）不重置选点编辑态

- 位置：`src/stores/fireStore.js` 中 `routeBuildingId` 的其它写点——`generateRoutePlans:2840`、`activateBuildingPlansFor:3256/3270/3277`，均不调用 `cancelAuthGraphSelection()`。
- 证据：`authoritativeRouteGraph` 是依赖 `routeBuildingId` 的 computed，会随其重算；但 `authGraphPath`/`authGraphDraftId` 是独立 ref，只在 `cancelAuthGraphSelection`/`resetAuthGraphSelection` 中清空。经 dashboard 切楼栋（触发 `activateBuildingPlansFor`）或自动规划（`generateRoutePlans`）改楼栋时，旧选点路径不清空。
- 影响：所有楼栋共享同一拓扑蓝本，旧路径拓扑仍合法，但保存时 `buildingId` 取自保存时刻楼栋，可能与被选点时刻楼栋不一致（轻微，实际安全影响小）。
- 建议：在 `routeBuildingId` 变化时（或 `authoritativeRouteGraph` 依赖失效时）重置编辑态，并补一条对应测试。

### F3【已满足 · 特别核对】下降边合法性不单靠楼层数字

- 位置：`src/stores/fireStore.js:1077–1087`。
- 证据：`canAuthStep` 先 `g.adj[fromId].some(e => e.to === toId)`（真实边存在），再 `floorNum(from) > floorNum(to)`（下降方向）。图中唯一跨层边为 `STAIR_DESCENT`（`floorTopology.stairDescentEdgeDefs` 按 `isStairActiveOnFloor` 门控），故联合判定充分；不存在仅凭楼层数字判断跨层的路径。
