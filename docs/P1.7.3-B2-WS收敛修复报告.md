## 一、B2-01 审计结论（先审计，再改代码）

**版本机制已经存在，缺的是仲裁和两处断链**：

| 消息 | 版本字段 | 前端现状 | 问题 |
|---|---|---|---|
| `demo.snapshot` / `demo.stage` / `demo.tick` | `seq = world.seq`（`world.ts:188`，`resetWorld` 保留 seq） | 只赋值、从不比较（`demoStore.js:91/130`） | 旧消息可覆盖新状态 |
| REST 命令响应 / `GET /state` | 同上（共用 `snapshot()`） | 无条件 `applySnapshot`（`:175`、`:146`） | 晚到的 REST 可覆盖更新的 WS |
| `demo.sync`（C→S） | 无 | **客户端 0 调用点**（服务端已实现 `DemoRoom.ts:148-151`） | 重连后不主动收敛 |
| `demo.pong`（S→C） | 无 | 空分支（`demoStore.js:133`） | 半开连接永不被发现 |

**字段完整性（B2-03）**：tick 是 snapshot 的真子集（`persons/metrics/evacuationSettled/seq/stage`），
前端「缺字段就不更新」→ **不会缩水**；`routePoints` 在 tick 中与 snapshot 同构下发，`applyDemoPersons` 按 id 合并，不会被清空。

## 三、每个改动点说明

### B2-02 单一版本仲裁

```
incoming.seq < local.seq  →  丢弃（console.warn，applySnapshot 返回 false）
incoming.seq >= local.seq →  接受（同 seq 视为同一版本，幂等）
seq 缺失                  →  按原行为放行（兼容老后端 / 本地构造消息）
```

覆盖四类入口：WS `demo.snapshot`、`demo.stage`、`demo.tick`，以及 REST 命令响应与 `GET /state`。
因此「旧 snapshot 覆盖新 tick」「旧 tick 覆盖新 snapshot」「晚到 REST 覆盖更新 WS」三条路径全部封死。

安全性依据：`RESET` 保留 seq（`engine.ts:86`）→ 复位不会让序号回退；阶段推进必伴随 `pushEvent` 的 `seq+1`，
tick 每次 `+1` → 单调性成立，正常链路不会误拒。

### B2-04 / B2-05 重连必须重新同步

```
ws.onclose → setStatus('reconnecting') → 指数退避 1/2/4/8/15s → connect()
   → onopen → startHeartbeat() + requestSync()          ← 本次新增
        → 服务端 DemoRoom.webSocketMessage('demo.sync') → demo.snapshot（全量）
             → demoStore.applySnapshot（seq 仲裁）→ fireStore.applyDemoSnapshot（收敛）
```

同时新增 **pong 超时判定**：`lastPongAt` 超过 `2 × 15s` 未更新即判定连接实际已断，主动 `close()` 触发退避重连，
避免「前端一直以为在线、状态永久落后」的半开连接场景。

### B2-06 断线期间前端不自行补状态

B1 已封锁 fireStore 全部旧本地写入；demoStore 无任何本地定时器（tick 只在后端），
3D 只做视觉插值不改 `progress/position`。B2 新增回归断言固化这一点（Case 5）。

### B2-03 字段完整性

无代码改动（审计结论：tick 缺字段即不更新，不会缩水）；转为回归断言（tick 后 `routePoints` 仍 ≥2、devices/fire/lighting 不清空）。
