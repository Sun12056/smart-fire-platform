## 一、消息与版本字段现状表

| 消息 | 方向 | 后端产生位置 | 版本字段 | 其他时间/序号字段 | 前端保存位置 | 当前问题 |
|---|---|---|---|---|---|---|
| `demo.snapshot` | S→C | `DemoRoom.handleWebSocketUpgrade:138`（建连即发）、`webSocketMessage` 处理 `demo.sync` `:150` | **`seq: world.seq`**（`world.ts:188`） | `tick`、`enteredAt`、`updatedAt`、`serverTime` | `demoStore.seq`（`demoStore.js:91`）**只赋值，从不比较** | 无仲裁：旧快照可覆盖新状态 |
| `demo.stage` | S→C | `DemoRoom.handleCommand:192`（RESET）、`:210`（阶段推进） | `seq`（取自 `snapshot()`） | 同上 | 同上 | 同上 |
| `demo.tick` | S→C | `DemoRoom.alarm:230-239`（仅 SMART_EVACUATION，每 tick `world.seq += 1`，`engine.ts:530`） | `seq` | `at` | `demoStore.seq`（`:130`）**只赋值** | 无仲裁；字段是 snapshot 的**子集** |
| `demo.sync` | C→S | —（服务端已实现 `DemoRoom.webSocketMessage:148-151`） | 无 | 无 | 不保存 | **客户端从未发送**（`demoClient.js:86` 定义了 `requestSync()`，全仓库无调用点）→ 重连后不主动收敛 |
| `demo.ping` | C→S | 客户端 `demoClient.startHeartbeat:76`（15s） | 无 | `at`（ISO） | 不保存 | 只发不收：无 pong 超时判定 |
| `demo.pong` | S→C | `DemoRoom.webSocketMessage:147` | 无 | `at` | **空分支**（`demoStore.js:133`） | 半开连接（网线断/代理假连）永远不会被发现，前端一直以为在线 |
| REST 命令响应 | S→C | `DemoRoom.handleCommand:193/219`（`{ok, ...snapshot(), events}`） | `seq`（同一 `snapshot()`） | `serverTime` | `demoStore.sendCommand → applySnapshot:175` **无条件覆盖** | 晚到的 REST 响应可覆盖更晚的 WS 状态 |
| REST `GET /state` | S→C | `DemoRoom.fetch:115-118` | `seq` | 同上 | `demoStore.connect:146` **无条件覆盖** | 同上 |

**结论①**：版本机制**已经存在且够用**——`DemoWorld.seq` 是会话级单调递增整数：
- `resetWorld` **保留** seq（`engine.ts:86`）→ RESET 不会让序号回退，可安全用于仲裁；
- `pushEvent`（`:96`）与 `tickWorld`（`:530`）各 `+1`，阶段推进一定伴随 seq 增长；
- snapshot / stage / tick / REST 响应**共用同一个 `snapshot()`**，seq 语义完全统一。

**结论②**：缺的不是字段，是**仲裁**（B2-02）和**两处断链**：`requestSync` 从未调用（B2-05）、pong 无超时（B2-04 半开连接）。

## 二、B2-03：snapshot 与 tick 字段完整性

`snapshot()`（`DemoRoom.ts:562-596`）全字段：

```
sessionId, seq, stage, stageIndex, stageLabel, nextCommand, nextStage, allowedCommands,
fire, alarmId, plans(LEGACY), activePlanId(LEGACY),
buildingPlans, activeBuildingPlanId, evacuationScope,
lighting, metrics, rescue, persons, devices, eventLog(30),
evacuationSettled, tick, enteredAt, updatedAt, serverTime
```

`demo.tick`（`DemoRoom.ts:230-239`）字段：

```
type, seq, stage, persons, metrics, evacuationSettled, at
```

| 类别 | snapshot | tick | 前端 tick 处理 | 是否会「缩水」 |
|---|---|---|---|---|
| 人员 `persons` | ✅ | ✅（`personDTOs`，与 snapshot 同一 DTO） | `demoStore:125` 整体替换；`fireStore.applyDemoPersons:497` **按 id 合并** | 否。`routePoints` 由 `normalizePersonRuntime` 同构产出（`shared/person/personRuntime.js:159`），tick 也带；`assignPersonRuntime:199` 仅在源字段存在时覆盖 → 不会把已有 routePoints 清空 |
| 设备 `devices` | ✅ | ❌ | `demoStore:127` `if (msg.devices)` 兼容分支；fireStore tick 不动设备 | 否（缺字段=不更新） |
| 火灾 `fire` | ✅ | ❌ | tick 不处理 | 否 |
| 灯光 `lighting` | ✅ | ❌ | tick 不处理 | 否 |
| 方案 `buildingPlans / activeBuildingPlanId / plans` | ✅ | ❌ | tick 不处理 | 否 |
| 救援 `rescue`、滞留 | ✅ | ❌ | tick 不处理（阶段变化必广播 `demo.stage`） | 否 |
| 阶段元数据 `stageIndex/stageLabel/nextCommand/allowedCommands` | ✅ | ❌ | tick 带 `stage` 但前端不消费 | 否（`demo.stage` 必达） |
| `metrics` | ✅ | ✅ | 双 store 同步 | 否 |

**结论③**：现有实现「缺字段就不更新」，因此**不会因为收到 tick 而缩水**，符合要求。
**遗留小缺口**（低风险，记录不处理）：tick 携带 `stage` 但前端不消费；若极端情况下 `demo.stage` 广播丢失，阶段会滞后到下一次 snapshot。B2 不额外补（避免把 tick 当权威快照用）。

## 三、B2-04 / B2-05：重连链路现状

```
ws.onclose (demoClient.js:54)
  → setStatus('reconnecting') → scheduleReconnect()        ← 指数退避 1/2/4/8/15s ✅
      → connect() → ws.onopen (:42)
          → retry=0 / setStatus('open') / startHeartbeat()  ← ❌ 没有 requestSync()
```

- 服务端**已经支持** `demo.sync`（`DemoRoom.ts:148-151`）→ 回送全量 `demo.snapshot`；
- 客户端**已有** `requestSync()`（`demoClient.js:86`）→ **0 个调用点**；
- `demoStore` 没有暴露任何触发入口。

**结论④**：重连后只能被动等下一次广播。IDLE / FIRE_DETECTED / ROUTE_PLANNING / RETAINED_PERSONS / RESCUE_COORDINATION 阶段**后端没有 tick**，重连窗口内若错过 `demo.stage` 广播 → 前端阶段永久落后于后端（正是 P1.7.3-07 禁止的「后端 A / 前端 B」）。

## 四、B2-06：断线期间前端是否会自行补状态

B1 已封锁 fireStore 全部旧本地写入（阶段 / 设备 / 方案 / 灯光）。断线期间：
- `demoStore` 无任何定时器（`alarm/tick` 只在后端）→ 不会自行推进；
- `fireStore` 的 mock 定时器（`updateRandomData`）仅在 **mock 模式**注册；
- 3D 的视觉插值只改渲染层，不改 `person.progress/position`。

**结论⑤**：断线 ≠ 前端重新成为权威，B1 之后已成立；B2 只需补「重连后能否收敛」。
